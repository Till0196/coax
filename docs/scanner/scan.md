# スキャン（`coax scan`）

`coax scan`はチャンネルを順に選局し、受信できたかどうかと、解析結果（PAT、NIT、SDT、サービス名、TSMF、TLV/MMTP）をJSONに保存します。
どの搬送波を調べるかは、`--discover`（内蔵の周波数リストから候補を組み立てる）、定義ファイル、[1チャンネルの指定](#1チャンネルだけ調べる)の3通りから1つを選びます。
このJSONがスキャン結果の元になり、Mirakurunなどの形式への変換は、あとから[`coax export`](export.md)で行います。

## 候補の確認（`--list`）

`coax scan --list`はデバイスを開かず、定義ファイルを読んだ結果だけをJSONで表示します。
スキャンの前に、定義ファイルが意図どおりに解釈されているかを確認できます。

```sh
./coax scan --list \
  ./channels-sat.conf
```

定義ファイルは引数で1つ以上指定します。
ファイル名は自由で、複数の伝送方式が混ざったファイルも使えます。
定義ファイルの書式は[channel-files.md](../reference/channel-files.md)にあります。

[1チャンネルだけ指定した場合](#1チャンネルだけ調べる)も、同じように確認できます（`./coax scan --ch 27 --list`）。
こちらは、チャンネル名から周波数と伝送方式が正しく決まるかを確認するためのものです。

## 実行する

衛星の定義ファイルをスキャンし、解析結果をJSONに保存する例です。
進捗は標準エラー出力に表示されます。

```sh
./coax scan \
  --output scan-sat.json \
  ./channels-sat.conf
```

`--output`を省くと、コマンドを実行した場所に`バックエンド_チューナー名_日付_時刻.json`（例：`chardev_dvb-adapter2.frontend0-0_20260829_143012.json`）を作り、そのファイル名を標準エラー出力に表示します。
チューナーや経路を変えて何度スキャンしても結果が上書きされず、あとからどのチューナーのいつの結果か分かるようにするためです。
標準出力に流したいときは`--output -`を指定してください。

チューナーを指定しなければ、定義ファイルの伝送方式を受信できる空きチューナーを`coaxd`が選びます。
指定する場合は、`--tuner px4:ABC12345@1-2.1:0`のように`coax list`に出た名前を渡します。
スキャンが終わるまで、そのチューナーを占有します。

経路ごとの例です。

```sh
# TBS6205SE: ISDB-T
./coax scan --tuner dvb:adapter2.frontend0:0 --output scan-ter.json \
  ./terrestrial.conf

# TBS6205SE: ISDB-C
./coax scan --tuner dvb:adapter2.frontend0:0 --output scan-catv.json \
  ./cable.conf

# PT4K: ITU-T J.83 Annex B
./coax scan --route HIKARI --output scan-hikari.json \
  ./flets.conf

# CATVの場合。トランスモジュレーションもBSパススルーも同じ線で届くので、
# 定義ファイルに両方入っていても --route は CATV だけです。
./coax scan --tuner dvb:adapter2.frontend0:0 --route CATV \
  --output scan-catv.json ./cable.conf
```

`/dev/dvb`が別の場所にある場合（コンテナーなど）は、`coaxd`の`--dvb-root`で指定できます。

## 1チャンネルだけ調べる

定義ファイルを使わず、コマンドラインでチャンネルを1つ指定することもできます。
使えるオプションと意味は[`coax tune`](../reference/tune.md#1チャンネルを受信するcoax-tune)と同じです。

```sh
./coax scan --ch 27                            # 地上波の物理27ch
./coax scan --ch BS15_1                        # 相対ストリーム付きの衛星
./coax scan --ch JCSAT3A/JD5                   # 124/128度のトランスポンダ
./coax scan --system ISDBT --freq 473142857
./coax scan --system ISDBS --freq 1318000 --stream-id 3
./coax scan --system DVBC/ANNEX_A --freq 471000000 -P SYMBOL_RATE=5274000
```

`--system`、`--ch`、`--freq`、`--stream-id`、`--lnb-power`、`--lnbf`、`--gain`、`--sat-number`、`-P NAME=VALUE`が使えます。
周波数で指定するときは`--system`も要ります。
`--ch`にチャンネル名や衛星のストリーム名を書いたときは、そこから伝送方式も周波数も決まるので要りません。

調べる搬送波の指定は、定義ファイル（引数）、`--discover`、この1チャンネルの指定のうち1つだけです。
2つ以上指定するとエラーになります。

結果は通常のスキャン結果と同じ形で、そのまま`coax export`に渡せます。
チャンネル名は`--ch`に書いたものになり、周波数で指定した場合は周波数（ストリームがあれば`周波数_ストリーム`）になります。
`source`は`command line`です。

`--include`と`--exclude`は効きません。
この2つは定義ファイルのセクションを選ぶもので、1チャンネルの指定では選ぶセクションが無いからです。

## ケーブルの`--discover`

ケーブルの`--discover`は、事業者のNITを読まずに、バンドプランの全波を決まった諸元で順に選局します。

| 方式 | 選局する周波数 | 諸元 |
| --- | --- | --- |
| ISDB-C（`DVBC/ANNEX_A`で受ける）| ケーブルのバンドプラン | `SYMBOL_RATE = 5274000`、`MODULATION = QAM/AUTO` |
| 光配信（`DVBC/ANNEX_B`）| 光配信のバンドプラン | `SYMBOL_RATE = 5600000`、`MODULATION = QAM/256` |

NITを先に読まないのは、ケーブルのNITから他の搬送波が分からないためです。
実測した系統では、どの搬送波のNITにもその搬送波自身しか書かれておらず、先に数波を選局しても候補は増えず、時間だけがかかります。

プランの諸元は日本の事業者がよく使う値です。
違うシンボルレートで運用している系統は、事業者の値を書いた定義ファイルを渡してスキャンしてください。

## 衛星のLNB給電（`--lnb-power`）

`--discover`や定義ファイルで衛星をスキャンするときも、`--lnb-power`が使えます。
`VOLTAGE`を書いていない衛星のチャンネルすべてを、その給電で選局します（NITを探すための選局も含みます）。
地上波やケーブルのチャンネルには付けません。
省略すれば給電しません。

```sh
./coax scan --discover ISDBS --lnb-power high
```

## 見つかったチャンネルの伝送方式

`--discover`が見つけたチャンネルの伝送方式は、そのチャンネルを見つけたときに選局した伝送方式になります。
BSとCSのTSは`ISDBS`、TLVは`ISDBS3`です。
NITは自分の網を記述するので、NITを読んだ多重と、NITに書かれている多重は同じ方式です。

ISDB-S3は、ISDB-Sとして選局し、ストリームの識別子で区別します。
1つの復調器が両方を受けるので、両者を分けているのはハードウェアではなく識別子です。
Linux DVB APIにはISDB-Sまでしか番号が無いので、`coaxd`はLinuxでは`ISDBS3`を`SYS_ISDBS`として渡します（識別子はそのまま渡します）。
Windowsのバックエンドは`ISDBS3`をそのまま扱うので、チャンネル側の名前は変えずにどちらでも使えます。

`coax export --format dvbv5`だけは`ISDBS`と書き出します。
libdvbv5にISDB-S3の番号が無いので、`ISDBS3`と書いたファイルは`dvbv5-zap`や`dvbv5-scan`で読めないからです。
これらのツールもISDB-Sとして選局するので、受信には影響しません。
Mirakurun、ChSet、`.ch2`は`ISDBS3`のまま出ます。

## `--route`（受信経路）

`route`（`TER`、`SAT`、`CATV`、`HIKARI`）は、チューナーのアンテナ端子がどの線に繋がっているかを表します。
伝送方式からは決められません。
1回のスキャンは1本のチューナーを最後まで使い、チューナーの端子も、その先の線も1本なので、`--route`はスキャンごとに1つです。
指定すると、そのスキャンで見つかったすべてのチャンネルに記録されます。

伝送方式から推定しないのは、同じ同軸にトランスモジュレーション（J.83）と衛星のパススルーが一緒に載るためです。
パススルーは電波のままのISDB-Sなので、アンテナから来たものと区別できません。
伝送方式で線を決めると、1本のケーブルが`CATV`と`SAT`に分かれ、Mirakurunに「このCATVのチューナーは衛星のチューナーでもある」と伝えることになります。
BSのパススルーは一部のトランスポンダだけのことが多いので、ケーブルに載っていないトランスポンダの録画にそのチューナーが選ばれ、録画が失敗します。

省略した場合は`route`を書き出しません。
Mirakurunが`type`から既定値（`GR`→`TER`、`BS`／`CS`／`SKY`／`BS4K`→`SAT`）を補うので、アンテナだけの構成ではそれで正しくなります。
CATVや光の線がある場合だけ指定してください。

## ISDB-S3（高度BS、高度CS）の書き方

Linux DVB APIにISDB-S3の番号が無いため、定義ファイルでは`DELIVERY_SYSTEM = ISDBS`のまま、`STREAM_ID`にTLVストリームIDを書きます。
ISDB-SかISDB-S3かは復調器が見分けるので、指定はStream IDだけで足ります。
ロックすると、`stream_format`が`tlv`のTLVストリームとして受信します（TSMFは通りません）。

```ini
[45168]
	DELIVERY_SYSTEM = ISDBS
	FREQUENCY = 1164560
	STREAM_ID = 45168
```

`DELIVERY_SYSTEM = ISDBS3`（`ISDB-S3`、`isdb_s3`も同じ）という書き方も使えます。
ISDB-Sとは別の伝送方式として扱いますが、ChSetやch2では衛星のファイルに入り、トランスポンダ名も衛星と同じ規則で付きます。
ただし、この名前が通るかどうかはバックエンドによります。
今はWindowsのバックエンド（BDA、TBSのPCIe）だけが受け付け、Linux DVB APIには番号が無いので通りません。
Linuxでは、上の`ISDBS`と`STREAM_ID`の書き方しかありません。

ISDB-SとISDB-S3は同じフロントエンド、同じ復調器で受けられるので、チューナーがISDB-Sにしか対応していないと申告していても、ISDBS3のチャンネルの選局を試します（逆も同じです）。
チューナーの申告だけで非対応と判断すると、実際には受信できるハードウェアでISDB-S3のチャンネルを飛ばしてしまうためです。

ISDB-S3のチャンネルだけをスキャンしたいときは、セクション名を正規表現で絞り込めます。

```sh
./coax scan \
  --include '^(45168|45169|45170|45232|45233|45234|45328|45329|45330|45280)$' \
  --output scan-isdbs3.json \
  ./channels-sat.conf
```

## ケーブル（J.83）のannexと定義ファイル

日本のCATVはITU-T J.83 Annex Cなので、対応するチューナーでは`DELIVERY_SYSTEM = DVBC/ANNEX_C`と書くのが正確です。
Annex AとAnnex Cの違いはロールオフ率（15%と13%）だけなので、Annex Cに対応していないチューナーでもAnnex Aとしてロックします。
`BANDWIDTH_HZ`はどちらでもシンボルレートから計算するので、省略できます。

### annexによる`MODULATION`と`SYMBOL_RATE`の扱いの違い

同じJ.83でも、Annex A/CとAnnex Bでは、定義ファイルに書く項目が違います。

| | Annex A / Annex C（`DVBC/ANNEX_A`、`DVBC/ANNEX_C`、`ISDB-C`）| Annex B（`DVBC/ANNEX_B`）|
| --- | --- | --- |
| `SYMBOL_RATE` | 必須。事業者が自由に決める値 | `t230`、`tbs5520se`は書けばその値、無ければ`MODULATION`から決める。`pxmlt`、`tbs5530`は必須で、5600000以上なら日本の光配信の設定 |
| `MODULATION` | 省略可。復調器が判別する | 5.057Msym/s（`QAM/64`）と5.361Msym/s（`QAM/256`）のどちらかを選ぶ材料 |
| `BANDWIDTH_HZ` | 省略可。シンボルレートとロールオフから計算 | 6MHz固定。別の値を書いても無視 |

Annex A/Cでは変調方式がほかの諸元と関係なく決まるので、復調器が変調方式を自動で判別します。
coaxも変調方式を復調器に渡さず自動判別に任せるので、`MODULATION = QAM/AUTO`のままでQAM64のチャンネルもQAM256のチャンネルも同期します。
必須なのは`SYMBOL_RATE`だけです。

```ini
[1]
	DELIVERY_SYSTEM = DVBC/ANNEX_A
	FREQUENCY = 93000000
	SYMBOL_RATE = 5274000
	MODULATION = QAM/AUTO
```

この例のように、日本のCATV（ISDB-C、つまりAnnex C）をAnnex Aと書いた定義ファイルはよくあります。
これは、Linux DVB APIでは`DTV_ENUM_DELSYS`に出てくる方式しか選べないためです。
Si2168のカーネルドライバーがその例で、Annex Aだけを出し、Annex CもISDB-Cも出しません。

```
$ dvb-fe-tool -a0
Device Silicon Labs Si2168 (/dev/dvb/adapter0/frontend0) capabilities:
...
CAN_QAM_64
CAN_QAM_256
CAN_QAM_AUTO
...
Supported delivery systems:
	DVBT
	DVBT2
	[DVBC/ANNEX_A]
```

3つは復調器のモードとしては同じなので、Annex Aと書いてもそのままロックします。
違いが出るのは`BANDWIDTH_HZ`を省略したときに計算される帯域だけです。
上の5274kSym/sなら、`DVBC/ANNEX_A`はロールオフ115%で6.07MHz、`DVBC/ANNEX_C`は113%で5.96MHz、`ISDB-C`は6MHz固定です。
この値はチューナーのチャンネルフィルターと復調器の帯域に渡るので、Annex Aと書いたときだけ少し広い帯域で受けることになります。
`dvb`バックエンド（Linux DVB）ではAnnex Aと書くしかありませんが、気になるなら`BANDWIDTH_HZ = 6000000`と書けば計算は使われません。
USBのデバイスを直接制御するバックエンド（`t230`など）は`DELIVERY_SYSTEM`を`coaxd`が解釈するので、`ISDB-C`や`DVBC/ANNEX_C`もそのまま書けます。

同じ理由で、T230のAnnex Bはカーネル経由では選べません。
上の一覧に`DVBC/ANNEX_B`が無いのは、メインラインのSi2168ドライバーがこの方式を実装していないためです。
TBSが配布しているドライバーか、`t230`バックエンドを使ってください。

Annex Bはトレリス符号化を使い、シンボルレートも変調方式で決まっています（64QAMは5.057Msym/s、256QAMは5.361Msym/s）。
そのため北米向けの定義ファイルは、`SYMBOL_RATE`ではなく`MODULATION`で書くのが普通です。
日本の光配信は5.6Msym/sで、この決まりから外れます。
どのバックエンドでも受信できるように、`SYMBOL_RATE`と`MODULATION`の両方を書いてください。

```ini
[ANNEX-B-EXAMPLE]
	DELIVERY_SYSTEM = DVBC/ANNEX_B
	FREQUENCY = 453000000
	SYMBOL_RATE = 5600000
	MODULATION = QAM/256
```

Annex Bの定義ファイルには、`MODULATION = QAM/AUTO`のものや、変調方式が書かれていないものもあります。
この方式でよく使われてきたLG系の復調器が、64QAMと256QAMをハードウェアで自動判別するためです。
Linuxの`lgdt3306a`ドライバーも、既定では常に自動判別で動きます。
一方、coaxが直接動かすSilicon Labs系（`t230`のSi2168、TBSのSi2183）にはこの自動判別がありません。
復調器がシンボルレートを判別できないので、coaxが決めて渡します。

`t230`（Si2168）と`tbs5520se`（Si2183）は、Annex Bのシンボルレートを次の順に決めます。

1. `SYMBOL_RATE`があればその値（日本の光配信の5.6Msym/sはこれで受けます）
2. `MODULATION = QAM/64`なら5.057Msym/s
3. それ以外は、デジタルケーブルで一般的な256QAMの5.361Msym/s

つまり、`SYMBOL_RATE`を書かずにAnnex Bで64QAMのチャンネルを受けるときは、`MODULATION = QAM/64`と書く必要があります。
自動判別の代わりに両方を試したいときは、同じ周波数で変調方式だけが違うセクションを並べてください（`dtv-scan-tables`もQAM64とQAM256でファイルを分けています）。

## 中断と再開

1チャンネル終わるごとに、進捗をJSONに保存します（書きかけのファイルが残らないよう、一時ファイルに書いてから置き換えます）。
進捗ファイルは、`--output`でファイルを指定したなら`<output>.progress.json`、それ以外（標準出力のときと、ファイル名を自動で付けるとき）は実行した場所の`.coax.progress.json`です。
次に実行したとき、定義、経路、選局のプロパティが同じチャンネルは、保存した結果をそのまま使います。
スキャンが最後まで終わると、進捗ファイルは消えます。

```sh
# 保存済み進捗を使わず最初から実行
./coax scan --restart ...

# 進捗ファイルを明示し、完了後も残す
./coax scan --progress scan.progress.json --keep-progress ...
```

定義ファイルで周波数やStream IDを変えたチャンネルは、保存した結果を使わずにスキャンし直します。

## 進捗と信号測定値の表示

端末で実行したときは、チャンネル数、ロック待ち、解析用に受信した量、経過時間を1行のプログレスバーで表示します。
標準エラー出力をファイルやパイプに向けたときは、チャンネルごとの1行表示に切り替わります。
進捗の段階は`tuning`、`locking`、`sampling`、`done`の4つです。

ロック待ちの行には、バックエンドが測定できた信号の値を、ステータス名に続けて表示します。
測定できないバックエンドでは何も表示しません。

```
[3/42] [########            ]  40% locking  ISDBT/22 SIGNAL,CARRIER,VITERBI,SYNC,LOCK CNR 28.5dB -42dBm quality 82% (1.2s)
```

バックエンドごとに何を測っているかは、各[ボード文書](../README.md#ボード別)の「信号測定」の節にあります。
C/Nは復調器がロックしている間しか意味が無いので、ロックしてから表示します。
信号強度はチューナーが測るので、ロックしない周波数でも表示されます（何も来ていない周波数と、強く入っているのに復調できない周波数を見分けられます）。
測定に失敗してもロックの判定には影響せず、値が出ないだけです。

## スキャンの解析時間

`--analysis-time`は上限です。
必要な情報がそろった時点で次のチャンネルへ進むので、通常は上限まで待ちません。
そろったかどうかは、結果を作るときと同じ解析を1秒ごとにかけ、各ストリームのサービスとネットワークが分かったかで決めます。
判定のために別の決まりを作ると、結果を作る解析と食い違うことがあるためです。
サービスやネットワークの情報を持たないストリームは条件を満たさないので、上限まで受信します。
早く終わった場合も、時間が短くなるだけで結果は変わりません。

指定しなければ、伝送方式ごとに次の値になります。

| 系統 | 上限 |
| --- | --- |
| ISDB-T / DVB-T / DVB-T2 | 5秒 |
| ISDB-S / ISDB-S3 / DVB-S / DVB-S2 | 22秒 |
| ケーブル（DVB-C 各種）| 22秒 |

指定すると、すべてのチャンネルが同じ値になります。

### 実測の根拠

次の値は、ストリーム自身の時計（TSはPCR、TLVはMMTPのタイムスタンプ）で測ったものです。

| ストリーム | テーブル | 周期 |
| --- | --- | --- |
| ISDB-T（UHF実波）| NIT | 0.98秒 |
| ISDB-C（地上波トランスモジュレーション）| NIT | 0.98秒 |
| ISDB-S（BS）| NIT | 10.00秒 |
| ISDB-S3（衛星）| TLV-NIT | 10.00秒 |
| ISDB-C上のTLV（トランスモジュレーション）| TLV-NIT | 10.00秒 |

参考: PAT 0.12秒、SDT 地上波/CATV 1.97秒、衛星 3.00秒。

周期だけでは上限を決められません。
テーブルの送出に時間のかかる中継器があるためです。
BS23（TSID 18288、13.0 Mbps）は、10秒周期のNITを、9.25秒かけて少しずつ流します。
受信を始めたときに途中まで流れていたセクションは必ず取りこぼすので、次の周期を待ってさらに9.25秒かかります。
その結果、最初に完全なNITが取れるのは約16秒後です（4回測って16.25〜17.10秒で、毎回同じ傾向）。
同じ設備のBS15（22.9 Mbps）は、送出に0.75秒、最初に取れるまで1.95秒です。

これは受信状態によるものではありません。
BS23はCNR 19.1dB（BS15より良い）、318,161パケット中で連続性カウンタの飛びもCRCの不良も0件、PID 0x10にNIT[other]もありません。
その中継器の送出の仕方によるものです。
そのため確実に取るには、送出の9.25秒と次の周期までの最大10秒で約20秒が要り、22秒はそれに余裕を足した値です。
実際にBS23は20.07秒で取れました。

ケーブルに衛星と同じ値を使っているのは、テーブルの周期が伝送路ではなく元のネットワークで決まるためです。
同じ設備で、地上波の再多重は3〜4秒、BSのトランスモジュレーションは11〜12秒でした。
ケーブルは衛星の多重をそのまま載せるので、テーブルの周期もそのまま届きます。

複数の搬送波に分割されたTSMFは、1波だけでは解析を完了できません。
多重フレームのヘッダーには搬送波の本数と自分の位置（`number_of_carriers`、`carrier_sequence`）が書かれているので、2本以上なら、この搬送波だけでは情報がそろわないと前もって分かります。
そのため、ヘッダーが取れた時点で打ち切ります（実測1.83秒）。
ケーブルで3波に分けられた放送（`carriers=3`、3波ともTSID 45280）の1波を80秒受信しても、TLV-NITは1回しか出てきませんでした。
10秒周期の3回に1回しかこの搬送波に載らないためで、受信時間を延ばしても増えません。

スキャン中の表示にも、`carrier 2/3`のように出します。
3分の1の多重からは情報も3分の1しか取れないので、表示しないと異常なチャンネルと区別できないためです。

分割された搬送波も、ほかと同じように書き出します。
1波だけ選局しても中身はそろいませんが、Mirakurunのフォークなどで複数の搬送波をまとめて受けられるようにしている場合、まとめる側には各搬送波の定義が要ります。
そのため、`number_of_carriers`を見て除外することはしません。

### `--max-bytes`による打ち切り

上限は時間とバイト数の2つあり、先に来たほうで受信を終えます。
バイト数の上限が解析時間に対して小さいと、そのチャンネルは警告なしに短く打ち切られます。
例えば、32 MiBでは38.9 Mbpsのケーブルの搬送波が6.6秒で上限に達し、10秒周期のNITが取れないまま終わります。
上限を上げると、そのチャンネルはNITが取れ、しかも早く終わります。
情報がそろった時点で次へ進めるためです。

| ch | 32 MiB | 96 MiB |
| --- | --- | --- |
| C19 | 8712ms NITなし | 2832ms NITあり |
| 13 | 8977ms NITあり | 3924ms NITあり |
| 23 | 10964ms NITなし×2 | 11422ms NITあり×2 |

既定の128 MiBは、最もビットレートの高い搬送波（ケーブルの256QAM、38.9 Mbps）の27秒分で、衛星とケーブルの上限の22秒より長く受けられます。
メモリーに保持するのは、常に1チャンネル分だけです。

## TLV探索（`--discover`）の打ち切り

TLVも探すときの衛星の`--discover`は、BS（TS）、CS（TS）、BS（TLV）、CS（TLV）の4段で探します。
TSの2段は、最初にロックした1波でネットワーク全体が分かって終わります（NITは網全体を記述するため）。
TLVの2段は、TLVが載っていない設備では24波をすべて試すことになり、打ち切らなければ探索時間の大半を占めます。

TLVを探しているので、TSだと分かった時点でその波は対象外です。
形式は同期バイトが8個続けば確定するので、そこで打ち切ります。
`unknown`（先頭が途中から始まっていて判定できない）では打ち切りません。
打ち切ると、TLVが載っている波を見落とすことがあるためです。

実測（PT3、同じ条件）では、打ち切らない場合の239秒に対して75秒です。
探索部分は約160秒が約68秒になり、残りはほとんどがロックしない波のタイムアウトです。
TLVを探さなければ17秒です。

```
BS TLV 3/12 BS05 ... not a TLV carrier                   ← 早期打ち切り
BS TLV 1/12 BS01 ... no TLV network table in the stream   ← 読めたがテーブルが無い
```

TLVを探すのは、`--discover`に`ISDBS3`を指定したときだけです。
`--discover`を伝送方式なしで使ったときに探さないのは、ISDB-S3だけです。

```sh
./coax scan --discover ...                # TLV探索なし。実測17秒
./coax scan --discover ISDBS ...          # 同上。20秒
./coax scan --discover ISDBS3 ...         # TLVだけ。62秒
./coax scan --discover ISDBS,ISDBS3 ...   # 両方。80秒
```

既定で探さないのは、チューナーがISDB-S3に対応しているかを、チューナーの申告から判断できないためです。
どの衛星チューナーも対応していると申告するので、それに従って24波を試すと、ほとんどの設備には無いネットワークのために、探索時間の4分の3を使うことになります。

チューナーの申告でISDB-S3への対応を判断することもしていません。
`dvb`と`bda`はOSのインタフェースを通すだけです。
Linux DVB APIにはISDB-S3の番号が無く（受けられる機器も受けられない機器も同じく`ISDB-S`と答えます）、Windows BDAには問い合わせる手段がありません。
coaxが直接制御するバックエンドは復調器が分かるので判断できますが、それを条件に飛ばすと、対応したデバイスを追加するときに一覧への登録が漏れただけで、ISDB-S3が警告なしに飛ばされます。
そこで、チューナーの申告は広めに受け取り、TLVを探すかどうかは利用者が`--discover`の指定で決める形にしています。

非対応のデバイスでの動作は次のとおりです。
TC90522で右旋の12波を選局すると、ロックしないのはTLVが載っている3波（BS07、BS11、BS17）だけで、ISDB-Sの9波は18〜20 dBでロックします。
信号が弱いのではなく、ISDB-S3は同じトランスポンダをより広い帯域と別の変調で使うので、そもそも復調できません。
ただし、これは選局してみるまで分からないので、探索の時間は減らせません。
そのため、伝送方式の指定で決める形にしています。

## 主なオプション

- `--tuner NAME`：使うチューナーを、`coax list`に出た名前で指定します。省略すると空いているものから選ばれます。
- `--host PATH`：`coaxd`のソケット（既定はOSごとの実行時ディレクトリ）。`host:port`も指定できます。
- `--no-start`：`coaxd`が起動していなくても、起動しません。
- `--firmware-dir PATH`：ファームウェアの置き場所。このコマンドが`coaxd`を起動したときだけ渡ります。起動済みの`coaxd`は、起動したときの設定のままです。
- `--route NAME`：チューナーの端子が繋がっている線（`TER`、`SAT`、`CATV`、`HIKARI`）。見つかったすべてのチャンネルに記録されます。省略するとMirakurunが`type`から補います。
- `--include REGEXP`：名前が一致するセクションだけをスキャンします。
- `--exclude REGEXP`：名前が一致するセクションを除きます。
- `--ch NAME`、`--freq HZ`、`--system NAME`など：定義ファイルの代わりに1チャンネルを指定します（[1チャンネルだけ調べる](#1チャンネルだけ調べる)）。`coax tune`と同じオプションで、意味も同じです。
- `--lock-timeout 5s`：チャンネルごとにロックを待つ時間。
- `--data-timeout 3s`：ロックしてからデータが届くのを待つ時間。
- `--analysis-time`：NIT、SDT、TSMFを解析するためにチャンネルを受信する時間の上限。必要な情報がそろえば早く次へ進みます。指定しなければ伝送方式ごとに決まり、地上波は5秒、衛星とケーブルは22秒です（[スキャンの解析時間](#スキャンの解析時間)）。指定すると、すべてのチャンネルで同じ値になります。
- `--max-bytes 128Mi`：1チャンネルで解析用に持つ最大バイト数。これに達しても受信を打ち切るので、解析時間ぶんの量が要ります（[`--max-bytes`による打ち切り](#--max-bytesによる打ち切り)）。
- `--min-bytes 3008`：受信できたとみなす最小の受信量。
- `--require-data=false`：データが届くのを確かめず、ロックしただけで受信できたとみなします。
- `--output PATH`：JSONの保存先。`-`なら標準出力に書きます。指定しなければ、コマンドを実行した場所に`バックエンド_チューナー名_日付_時刻.json`（例：`chardev_dvb-adapter2.frontend0-0_20260829_143012.json`）を作り、ファイル名を標準エラー出力に表示します。
- `--resume=false`：保存してある進捗を使いません。
- `--restart`：保存してある進捗を消してから始めます。
- `--progress PATH`：進捗ファイルの場所。

全体の使い方は`./coax -h`で、サブコマンドごとの使い方は`./coax scan -h`のようにして確認できます。

## 解析の制限

MMTPでは、サービスを見つけるのに要るシグナリングとMH-SDTだけを解析します。
映像や音声のMPU、字幕、番組表はスキャンでは扱いません。

複数の搬送波に分けて送るTSMFは、搬送波どうしを時間で揃えて組み直す必要があります。
coaxは1つの搬送波から取ったサンプルで分かる範囲だけを解析し、搬送波を組み直したり続けて受信したりはしません。
1つの搬送波で完結するTLVでは`invalid_packets`はほぼ0ですが、複数の搬送波に分けられたものは不完全なTLVを受けることになるので、大きな値になります。

バックエンド（USBチューナー、Linux DVB API、Windows BDA）による制限は、[daemon.md](../daemon.md#制限事項)と各[ボード文書](../README.md#ボード別)にあります。
