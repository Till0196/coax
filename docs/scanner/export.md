# エクスポート（`coax export`）

`coax scan`が保存したJSONから、各ソフトウェア向けのチャンネル定義ファイルを書き出します。
デバイスは開かないので、書き出し方を変えるだけならスキャンし直す必要はありません。

| `--format` | 出力 | 読む側 |
| --- | --- | --- |
| `mirakurun`（既定）| `channels.yml` | Mirakurun |
| `dvbv5` | `*.conf` | `dvbv5-zap` |
| `chset` | `*.ChSet.txt` | BonDriver_PT3-ST、BonDriver_PX4 |
| `ch2` | `*.ch2` | TVTest |
| `chset4`／`chset5` | `ChSet4.txt`／`ChSet5.txt` | EDCB |

## スキャン結果のJSON

`coax scan`は常にJSONを書き出します。
JSONには、すべての候補の結果（`found`、`no_lock`、`no_data`、`unsupported`、`error`）、選局の設定、フロントエンドの状態、受信バイト数、PAT、NIT、SDT、サービス名、TSMFの搬送波の情報、すべての相対ストリーム、TLV、MMTP、MH-SDTの解析結果が入ります。
Mirakurunなど特定の形式に合わせる段階で情報を落とさないよう、このJSONをスキャン結果の元として、各形式はここから書き出します。

TLVは、TLVパケットの境界、IPv4/IPv6とヘッダー圧縮IP、UDP、MMTPヘッダー、分割・集約されたMMTシグナリング、TLV-NIT、MH-SDTまで解析します。
JSONには、パケットの種類ごとの数、MMTPのフロー、Packet ID、Network ID、TLV Stream ID、ONID、サービスの情報が入ります。
TSMFの中のTLVの相対ストリームも、PID `0x2d`からTLVのバイト列を組み立て直して同じように解析します。

NITは、Network IDごとに`networks`に記録します。
ネットワーク名、多重ごとのTransport Stream ID、Original Network ID、サービスの一覧のほか、地上デジタル放送ではARIBのTS情報記述子からリモコン番号とTS名も取ります。
自ネットワーク（table_id `0x40`）と他ネットワーク（`0x41`）は`actual`で見分けます。
まだ選局していない多重があることも分かるので、定義ファイルを作るときの手がかりになります。
TLVも同じように、TLVストリームとそのサービスを`networks`に記録します。

TSMFの`decoded_frames`は、サンプルから読み取れたフレームの数です。
受信バイト数を188と53で割った値と大きく違うときは、受信かフレーム同期に問題があります。

## Mirakurun形式（`channels.yml`）

```sh
./coax export \
  --input scan-sat.json \
  --output channels-scanned.yml
```

`--route`は、スキャンが記録した値を上書きします。
どの線かは信号からは判別できないので、スキャン時の指定を誤っても、スキャンし直しては修正できません。
書き出し直すだけで修正できます。

`channel`の書き方は`--channel-name`で選べます。
既定の`scanned`はスキャンが付けた名前（衛星なら通常はStream ID）で、`transponder`は衛星のチャンネルをrecpt1式（`BS15_1`）に直します。
効くのはISDB-Sだけで、地上波やケーブルにはトランスポンダが無いので元の番号のままです。

```sh
./coax export --input scan-sat.json --channel-name transponder --output channels-sat.yml
```

名前がStream IDでなくても、`FREQUENCY`と`STREAM_ID`から位置を求めるので、任意のセクション名を付けた定義ファイルのスキャン結果でも変換できます。

ISDB-S3（高度BS、高度CS）のTLVストリームは、Stream IDのまま残します。
TLVの多重を受けられるドライバーは、どれもStream IDで選局します。
「このトランスポンダの最初のストリーム」と書くと、同じトランスポンダに載っているISDB-Sのサービスを指してしまい、選局は成功するのに別のストリームを受信するためです。
変換しなかったチャンネルは、理由と一緒に標準エラー出力に出します。

### 既定で出力する項目

既定で書き出すのは、名前、種別、位置の最小限だけです。

```yaml
- name: "サンプル衛星"
  type: BS
  channel: "BS15_1"
```

`name`は、`--service-id`を付けない既定（1エントリ＝1チャンネル）では、放送の種類で決まります。
地上波、BS、高度BSは、先頭のサービスの名前です。
多重が1つの放送局のものなので、先頭のサービス名がそのままチャンネルの通称になります。
110度CS、高度CS、124/128度CS、ケーブル事業者の自主放送は、搬送波の名前（`ND02`、`C32`）をそのまま使います。
[ChSet形式](#bondriver向けチャンネル定義ファイルchset)のチャンネル名と同じ決まりで、理由も同じです。
これらは枠ごとに別の事業者が使っている、互いに関係の無いチャンネルの集まりなので、先頭のチャンネルはほかを代表せず、事業者が入れ替わるとスキャンし直すたびに名前が変わります。
サービス名は、Mirakurunのサービススキャンがストリームから読むので失われません。
`--service-id`を付けたときは、1エントリが実際に1つのサービスを指すので、どの種類でもサービス名を書きます。

TSMFで複数のストリームが載っている搬送波は、`tsmfRelTs`ごとに別のエントリになります。
搬送波の名前で書く場合は、`C32_1`、`C32_2`のように相対TS番号を付けて区別します。

`serviceId`、`tsmfRelTs`、`route`は、既定では書きません。
Mirakurunは最初にサービススキャンをして、その後も定期的に繰り返します。
`serviceId`の無いエントリは「そのチャンネルのすべてのサービス」として扱われるので、放送局がサービスを増減しても追従できます。
TSMFのフレームもMirakurunが検出します。
これらを書き出すと、スキャンした時点の状態にリストが固定されます。
そのため、既定では1チャンネルにつき1エントリです。

`isDisabled`は、SDTの`free_CA_mode`（そのサービスが限定受信（CA）の対象か）で決めます。
チャンネルのすべてのサービスがCAの対象のときだけ`isDisabled: false`を書き、それ以外では項目そのものを書きません。
CAの対象でないサービスが1つでもあれば、そのチャンネルを受信する意味があるためです。

値は常に`false`です。
カードがあるかどうかはストリームからは分からないので、coaxがチャンネルを無効にすることはしません。
この項目は、手で`true`にするかどうかを判断する箇所の目印です。
項目が無いチャンネルもMirakurunの既定で`false`なので、扱いは同じです。

CAの対象かどうかはSIに書かれている事実ですが、契約しているかどうかはストリームからは分かりません。
見ているのはCAの状態であって、有料かどうかではありません。

必要な場合だけ足せます。

| オプション | 出力 | 用途 |
| --- | --- | --- |
| `--service-id` | サービスごとに1エントリ、`serviceId`付き | 編成を固定したいとき |
| `--tsmf-rel-ts` | 相対TSごとに1エントリ、`tsmfRelTs`付き | どの相対TSかを明示したいとき |
| `--route NAME` | `route: NAME` | [受信経路](scan.md#--route受信経路)を明示するとき。`scanned`でスキャンが記録した値 |

```sh
./coax export --input scan-catv.json --route CATV --tsmf-rel-ts --output channels-catv.yml
```

この中で、信号から判別できないのは`route`だけです。
ほかはMirakurunが検出できるので、必要なときだけ足してください。

`--tsmf-rel-ts`を付けても、相対TSが1本しかない搬送波には番号を書きません。
区別する必要が無いためです。
1本の搬送波に種別の違うチャンネルが載っている場合（TSMFで地上波と衛星が一緒に載っているなど）は、既定でも種別ごとに分けて書き出します。

TSMFの解析結果はすべてJSONに残しますが、Mirakurun形式に書き出すときは、通常は`tsmfRelTs`を固定しません。
Mirakurunがチャンネルの中のストリームをすべて検出するので、同じ物理チャンネルを相対TSごとに重ねて登録する必要はありません。

### typeの決め方

Mirakurun形式では、SDTかMH-SDTから取ったサービス名とService IDを使い、typeはNetwork IDで決めます。

| Network ID | type |
| --- | --- |
| `0x0004` | `BS` |
| `0x0006`、`0x0007` | `CS` |
| `0x000B`（高度BS）、`0x000C`（高度CS）| `BS4K` |
| `0x7880`〜`0x7FE8`（地上デジタル放送）| `GR` |
| `0x0001`、`0x0003`、`0x000A`（124/128度CS）、`0xFFF7`以上（ケーブル事業者の自主放送）、その他の有効なNetwork ID | `SKY` |

MirakurunにはCS4Kが無いので、高度CSも`BS4K`にまとめます。
TSかTLVかといった伝送方式は、typeの判定に使いません。
地上波は、物理チャンネルごとに最初のサービス名を1つだけ使います。

typeとrouteは別々の軸です。
typeは「どの放送か」でNetwork IDから決まり、routeは「どの線から来たか」で人が指定します。
Network IDが取れなかったTSは、伝送方式やrouteからtypeを推測せず、Mirakurun形式には書き出しません。
こうすることで、トランスモジュレーションされた放送も、受信経路によらず元の放送のネットワークで分類されます。

DVB-S2のチャンネルには、既定で`commandVars.satellite`を書き出します。
`route`と同じく、信号から判別できない項目のためです（詳しくは[dvb-s2.md](dvb-s2.md)）。

## DVBv5チャンネル定義ファイル（`dvbv5-zap`）

`--format dvbv5`で、`dvbv5-zap`が読むチャンネル定義ファイルを書き出します。

```sh
./coax export --format dvbv5 --input scan.json --output dvbv5_channels
# wrote dvbv5_channels_ter.conf
# wrote dvbv5_channels_catv.conf
```

1つのセクションは1回の選局に当たり、サービスやroute、相対TSを書く欄はありません（`dvbv5-zap`は搬送波を選局して、載っているものをすべて出力します）。
そのため、スキャン結果の1件がちょうど1セクションになります。

プロパティは、スキャンに渡されたときの書き方のまま書き戻します。
ロックしたのはその書き方での選局で、`DELIVERY_SYSTEM`をどう解釈するかはバックエンドが決めることだからです（`config.NormalizeDeliverySystem`は名前を認識するだけで、書き換えはしません）。
並び順は、`DELIVERY_SYSTEM`と`FREQUENCY`が先で、残りはアルファベット順です。

### ISDB-S3の書き出し方

ISDB-S3のチャンネルは、スキャン結果には`ISDBS3`と記録されていますが、この形式では`ISDBS`として書き出します。
libdvbv5にISDB-S3の番号が無いので、`ISDBS3`と書いたファイルは`dvbv5-zap`でも`dvbv5-scan`でも読めません。

これで受信に影響はありません。
ISDB-S3はISDB-Sと同じ復調器で受けるもので、両者を分けているのは`STREAM_ID`です。
`STREAM_ID`はそのまま書かれるので、`dvbv5-zap`がこのファイルで選局すればTLVストリームが出ます。

`ISDBS3`のまま書き出すのは、Mirakurun、ChSet、`.ch2`です。
これらは伝送方式をそれぞれの形式の言葉に置き換えて書くので、番号の制約がありません。

### routeごとのファイル分割

routeごとにファイルを分けるのは、読む側がその単位で使うからです。
`dvbv5-zap`はチューナー1台にファイルを1つ指定し、チューナーには端子が1つ、端子には線が1本つながっています。
形式としては分ける必要はありません（セクションごとに`DELIVERY_SYSTEM`を持つので、J.83にトランスモジュレーションされたチャンネルと、同じ番号でパススルーされているISDB-Tは、1つのファイルに入れられます）。
分ける必要があるのはセクション名のほうで、地上波の27chとケーブルの27chはどちらも`27`になり、1つのファイルには両方入りません。

`--output`はファイル名ではなく接頭辞で、後ろに`_ter`、`_sat`、`_catv`、`_hikari`と`.conf`が付きます。
routeを記録していないスキャン（`coax scan --route`を付けなかった場合）は`<接頭辞>.conf`になります。
`--route NAME`を付けると、その線のファイルだけを書きます。
標準出力に書けるのは、書くファイルが1つのときだけです。

### 地上波のファイルが書く範囲

地上波は、スキャンで何も見つからなかった物理チャンネルも、空のセクションとして書き出します。
読む側は周波数で選局するだけで、そこに何が載っているかを使わないためです。
配布されている`dvbv5_channels_ter.conf`も、プランの113チャンネルをすべて、中身に関係なく並べています。
1回のスキャンで受信できたものだけのファイルでは、障害から戻った局、スキャンが途中で止まって届かなかった局、隣の家では映る局を、あとから選局できません。

空のセクションを足すのは地上波だけで、しかもその線で地上波が見つかったときだけです。
スキャンできなかったケーブルのチャンネルにはシンボルレートと変調方式が要りますが、これは事業者ごとに違い、どのプランにも載っていません。
応答しなかったトランスポンダにはストリームIDが要りますが、それはそのトランスポンダのストリームからしか分かりません。

空のセクションは、同じ線でスキャンしたチャンネルと同じ書き方で書きます。
`ISDB-T`と書いたファイルに、`ISDBT`と書いたセクションが113個並ぶことのないようにするためです。
すでにあるセクションと名前が重なる場合は書きません（そのチャンネルは、その番号に載っている別のものとしてファイルにすでにあります）。

### セクション名（`--channel-name`）

既定の`scanned`はスキャンが付けた名前で、衛星なら通常はストリームIDです（`[16625]`）。
`transponder`にすると、recpt1式（`[BS15_1]`）になります。

```sh
./coax export --format dvbv5 --channel-name transponder --input scan-sat.json --output dvbv5_channels
```

セクション名はただの名前で、実際にストリームを選ぶのは`STREAM_ID`プロパティです。
名前を変えても、選局の動きは変わりません。
それでも選べるのは、Mirakurunの`channels.yml`の`channel`がこのセクション名と一致していなければならないからです。
選択肢はMirakurun形式の`--channel-name`とそろえてあります。

TLVストリームは、Stream IDのまま残します（理由はMirakurun形式と同じです）。
名前を付け替えなかったものは理由と一緒に標準エラー出力に出し、ファイルにはスキャンが付けた名前で入ります。

`--service-id`と`--tsmf-rel-ts`は、この形式では意味が無いので、指定するとエラーになります。

### アンテナ側の設定（`--lnbf`／`--sat-number`）

スキャンが記録した選局のプロパティはそのまま書き戻します。
そのため、元の定義ファイルに`LNB`があったスキャンや、`--discover`で124/128度を探したスキャン（プランから`LNB`と`POLARIZATION`を埋めます）では、それがそのまま書き出されます。
記録されていない設備側の設定は、書き出すときに足せます。

| オプション | 書く欄 | 用途 |
| --- | --- | --- |
| `--lnbf NAME` | `LNB` | アンテナのLNB。`UNIVERSAL`、`EXTENDED`、`ENHANCED`、`STANDARD`、`DBS`、`C-BAND`、`110BS`、`JCSAT3A`、`JCSAT4B` |
| `--sat-number N` | `SAT_NUMBER` | DiSEqCスイッチのポート（0〜3）。アンテナがスイッチを挟んで繋がっているとき |

```sh
./coax export --format dvbv5 --input scan-sky.json --lnbf JCSAT3A --sat-number 1 --output dvbv5_channels
```

どちらもlibdvbv5自身のキー（`DTV_DISEQC_LNB`と`DTV_SAT_NUMBER`）なので、書いたファイルは`dvbv5-zap`でもcoaxでも同じ意味になります。
すでにその欄があるセクションは上書きしません。
スキャンが記録したのは実際にロックした値で、あとからコマンドラインで指定された値より確実なためです。

LNBの名前は、LNBfテーブルと突き合わせません。
テーブルを持つのは`coaxd`で、ここに複製を置くと、同期を保つ対象が1つ増えます。
また、`dvbv5-zap`向けのファイルには、coaxが持たないLNBの名前が書かれていても問題ありません（`coax tune --lnbf`が名前をそのまま渡すのと同じ理由です）。

`--lnbf`はISDB-Sには書きません。
`LNB`は設備のメモではなく、「この周波数はダウンリンク周波数なので、局部発振周波数を引くこと」というチャンネルの指示です（`coaxd`の`ApplyLNBf`）。
日本の衛星のチャンネル定義ファイルはすでに中間周波数で書かれているので、そこに`LNB`を書くと、引いたあとの値から局部発振周波数をもう一度引くことになります。
値は正しく見えても、ロックしないファイルになります。
そのため、ダウンリンク周波数で書かれるDVB-S/DVB-S2のセクションにだけ書き、それ以外には書かずに理由を標準エラー出力に出します。

`SAT_NUMBER`にはこの区別はありません。
スイッチは線の途中にあるもので、アンテナがどのポートに繋がっているかは、周波数の意味に関係なく同じだからです。

なお、`VOLTAGE`（`coax tune --lnb-power`が使う欄）はこの形式には書けません。
libdvbv5のconfのキーではなく（DVBv3から来たもので、`dvbv5-zap`は`POLARIZATION`から電圧を決めます）、書いても読む側が無視するだけです。

## BonDriver向けチャンネル定義ファイル（ChSet）

`--format chset`で、BonDriver_PT3-STやBonDriver_PX4が読む形式のチャンネル定義ファイルを書き出します。
PT3やpx4_drvを使っている環境に定義ファイルを用意するためのものです。

```sh
./coax export --format chset --input scan.json --output BonDriver_coax
# wrote BonDriver_coax-T.ChSet.txt
# wrote BonDriver_coax-S.ChSet.txt
```

伝送方式ごとに1つのファイルになります。
この形式には伝送方式を書く欄が無く、読む側が`chset_t.Load(path, ISDB_T)`のようにファイルごとに指定するためです。
そのため`--output`はファイル名ではなく接頭辞で、後ろに`-T`（ISDB-T）、`-S`（ISDB-S）、`-C`（ISDB-C）、`-H`（J.83 Annex B、光）、`-S2`（DVB-S2）が付きます。
標準出力に書けるのは、伝送方式が1つのときだけです。

```
;
; channel definitions (ISDB-S), written by coax
; load this file as ISDB-S; the file it is has to say so, because the format does not
;
; spaces ($name<TAB>space id)
$BS	0
$CS	1
;
; channels (name<TAB>space id<TAB>channel id<TAB>physical channel<TAB>TSID)
; [BS]
BS15/TS0	0	0	7	16625
BS15/TS1	0	1	7	16626
; [CS]
ND02	1	0	12	24608
```

`physical channel`はドライバーが使うチャンネル番号（`PTX_SET_CHANNEL`が取る`freq_no`）で、スキャン結果の周波数から求めます。
地上波の27chは77、C23は22、BS15は7、ND02は12です。
改行はCRLFで、文字コードはCP932です（BonDriver_PX4が名前を`ShiftJisToUtf16`に通すので、ほかの文字コードは使えません）。

地上波のファイルには、すべてのチャンネルが入ります。
スキャンで何も見つからなかった物理チャンネルも、名前と番号だけの行になります。
理由はDVBv5と同じで（[地上波のファイルが書く範囲](#地上波のファイルが書く範囲)）、ドライバーは物理チャンネル番号を周波数に戻して選局するだけのためです。
BonDriver_PX4に付いているファイルも、113チャンネルをすべて、中身に関係なく並べています。
プランが隙間なく並ぶので、`channel id`と`physical channel`はすべてのチャンネルで同じ番号になります。

```
1Ch	0	0	0	0
C13Ch	0	3	3	0
C22Ch	0	12	12	0
4Ch	0	13	13	0
27Ch サンプルテレビ	0	77	77	0
62Ch	0	112	112	0
```

ケーブルと衛星では、空の行を足しません。
ケーブルのチャンネルに何が載るかは事業者によるので、スキャンできなかったチャンネルがどの空間に入るかはプランからは分かりません（空間はストリームのネットワークIDで決まり、何も来ないチャンネルにはネットワークIDがありません）。
衛星では、応答しなかったトランスポンダには名前の元になるストリームが無いので、空の行を足す必要がありません。

チャンネル名には代表のサービス名を付けます。
搬送波の名前は場所しか表さないので、`27Ch`のように番号で局が分かる地上波はともかく、`BS01/TS0`は一覧を見ないと何のチャンネルか分かりません。
先頭のサービス名を、空白で区切って足します（列の区切りはタブなので、名前に空白が入っても問題ありません。BonDriver_PX4もタブだけで区切って読みます）。

```
BS01/TS0 サンプル衛星	0	0	0	16400
ND04/TS0 サンプル！ドラマＴＶ	0	2	13	28736
```

CP932に無い文字（ARIB外字など）を含むサービス名は足さず、搬送波の名前のままにします。
この形式にはch2のようにUTF-16に切り替える手段が無く、名前が化けた一覧より、搬送波の名前だけの一覧のほうが使いやすいためです。

代表のサービス名が付くのは`GR`、`BS`、`BS4K`だけです。
これらは多重が1つの放送局のものなので、先頭のサービス名がそのままチャンネルの通称になります。

同じトランスポンダに複数のストリームが載っている場合だけ、`/TS0`、`/TS1`を付けます。
番号はTSIDの順に振るので、同じ設備を2回スキャンすれば同じファイルになります。
ストリームが1本だけのトランスポンダには付けません。

番号は空間をまたいで振ります。
2Kと4Kが同じトランスポンダに載っている場合（110度CSではよくあります）、2Kは`ND04/TS0`で`CS`空間、4Kは`ND04/TS1`で`CS4K`空間になります。
場所はトランスポンダで決まるもので、空間で決まるものではないからです。
空間ごとに振ると、同じ物理チャンネルの別のストリームがどちらも`ND04`になり、見分けが付かなくなります。

Mirakurun形式向けのオプション（`--route`、`--service-id`、`--tsmf-rel-ts`、`--channel-name transponder`）は、この形式では意味が無いので、指定するとエラーになります。
書けない指定を無視せず、エラーとして知らせるためです。

## TVTest向けチャンネル設定ファイル（ch2）

`--format ch2`で、TVTestが読むチャンネル設定ファイルを書き出します。
ChSetはBonDriverに搬送波の位置を渡すファイルで、ch2はTVTestにその搬送波に載っているサービスを渡すファイルです。
2つで1組になります。

```sh
./coax export --format ch2 --input scan.json --output BonDriver_coax
# wrote BonDriver_coax-T.ch2
# wrote BonDriver_coax-S.ch2
```

```
; TVTest チャンネル設定ファイル
; 名称,チューニング空間,チャンネル,リモコン番号,サービスタイプ,サービスID,ネットワークID,TSID,状態
; written by coax for ISDB-S
;#SPACE(0,BS)
テスト　衛星,0,0,1,1,101,4,16625,1
テスト　衛星４Ｋ,0,0,2,1,102,4,16625,1
```

「チューニング空間」と「チャンネル」は、ChSetファイルの`space id`と`channel id`そのものです（地上波では、空きチャンネルも含めたプランの中での位置なので、27chは77になります）。
TVTestはこの2つでBonDriverに選局を要求するので、番号は、読み込まれるChSetファイルの並びと一致していなければなりません。
違う並びで書かれた`.ch2`は、番号はどれも正しく見えるのに、エラーにならずに別のチャンネルを指します。
そのため2つの形式は同じ計算で番号を振っていて、`--output`に同じ接頭辞を渡せば、1組のファイルがそろいます。

「リモコン番号」は、放送が申告しているならその値をそのまま使います。

- TLV：TLV-NITのリモコンキー記述子（`0xCD`、第1ループ）に、サービスごとの値が書かれています。ARIB TR-B39 36.1.2.3で「TLV-NIT[actual]を送出する際は必ず配置する」と決められている記述子で、STD-B60 5.3.1.5のとおり「個数＋1件5バイト」で並びます。TLVのサービスは、TSのサービスと同じサービスIDを別のネットワークIDで使うので、サービスIDから計算しても正しい番号は出ません。この記述子から読む必要があります。
- 地上波：各局がNITのTSループのTS情報記述子（`0xCD`）に書いている値（多重ごとに1つ）。
- BS、CS、124/128度CS：記述子が無いので、TVTestと同じ決まりでサービスIDから求めます（BS 101〜103は「−100」、BS 141〜229は「−100して÷10」、124/128度CSは「−32768」）。

分からないものは0にします。
TVTestは0を「未設定」として扱い、必要ならサービスIDで代用します。

TLVと地上波の値は、どちらもNITから取ります。
TLVのリモコンキー記述子はTLV-NITの第1ループ（ネットワーク名記述子と同じ場所）に、地上波のTS情報記述子はNITのTSループにあります。
衛星の既定の上限22秒は、NITの送出周期と送出にかかる時間（実測、[スキャンの解析時間](scan.md#スキャンの解析時間)）から決めた値なので、通常はそのままで取れます。
取れなかったTLVのサービスは上の計算に回り、`401`や`141`のようなサービスIDがそのまま入ります。

対応している放送は`--format chset`と同じで、地上波、CATV（事業者の自主放送を含む）、BS、110度CS（ONID 6と7の両方を1つの`CS`空間に）、BS4K/CS4K、124/128度CS（衛星と光配信の両方）です。
110度CSはチャンネル番号がそのままサービスIDなので（Ch.310はサービスID 310）、リモコン番号は計算せず、サービスIDをそのまま書きます。
TVTestも同じ扱いです。
TSMFで多重されたケーブルの搬送波は、スロットごとに、元のネットワークIDが示す空間に振り分けます。
同じ搬送波に載っているトランスモジュレーションのBSは`BS`空間に、事業者の自主放送は`CATV`空間に、という具合です。
ISDB-Cとして受信できる以上、そのBSは一度復調してJ.83で変調し直したトランスモジュレーションです。
パススルーは電波のままのISDB-Sなので、同じ線でもISDB-Sとしてスキャンされ、別のファイルになります。
TSIDの欄には、各ストリーム自身のTSIDを書きます（ChSetのTSID欄は「どのストリームを取るか」を表しますが、こちらはストリームを見分けるための値なので、ストリームが1本の搬送波でも実際の値が入ります）。

サービスが1つも取れなかった空間は、`;#SPACE`の行ごと書きません。
空の空間を書いてもTVTestには何も出ず、スキャンが失敗したように見えるためです。
このとき、残りの空間はChSetと同じ番号のままなので、抜けた番号はどこからも使われない空き番号になります。

文字コードはCP932で、名前がCP932で書けなければBOM付きUTF-16LEに切り替えます。
TVTestは先頭2バイトがBOMならUTF-16、そうでなければCP932として読むので、UTF-8で書くと文字化けしたまま読み込まれます。
ARIB外字を含むサービス名はCP932では書けないので、UTF-16になります。
この切り替え方は、TVTest自身が保存するときと同じです。

ファイル名は、BonDriverに合わせて（`BonDriver_PX4-S.ch2`のように）利用者が決めるものなので、`--output`は接頭辞です。
必要に応じて名前を変えてください。

EDCBはこの形式を直接は読みませんが、`--format chset4`、`--format chset5`でEDCB用のファイルを書けます（次の節）。
`.ch2`から変換したい場合は、EDCBに付いている`EdcbPlugIn/ch2chset.vbs`が使えます。
このスクリプトはBOM付きUTF-16LEもBOM無しCP932も見分けるので、どちらで書かれていても読めます。

## EDCB向けチャンネル情報（ChSet4.txt / ChSet5.txt）

EDCBのファイルは2種類あります。
`ChSet4.txt`はチューナー1台（BonDriver 1つ）ごとのファイルで、1サービス1行です。
`ChSet5.txt`はEDCB全体で1つのファイルで、どのチューナーで見つけたかに関係なく、すべてのサービスを1行ずつ持ちます。
役割が違うので、別々のコマンドで書きます。

```sh
./coax export --format chset4 --input scan.json --output BonDriver_coax
# wrote BonDriver_coax-T().ChSet4.txt
# wrote BonDriver_coax-S().ChSet4.txt

./coax export --format chset5 --input scan.json --output ChSet5.txt
```

```
# ChSet4.txt（タブ区切り12列、見出し行なし）
# チャンネル名 サービス名 ネットワーク名 チューナ空間 物理チャンネル ONID TSID SID サービスタイプ 部分受信か 一覧表示に使用するか リモコンID
BS15 テスト　衛星	テスト　衛星	ＢＳデジタル	0	0	4	16625	101	1	0	1	0

# ChSet5.txt（タブ区切り9列）
# サービス名 ネットワーク名 ONID TSID SID サービスタイプ 部分受信か EPGデータ取得対象か デフォルト検索対象か
テスト　衛星	ＢＳデジタル	4	16625	101	1	0	1	1
```

「物理チャンネル」列は、物理チャンネル番号ではありません。
列の名前とは違い、EDCBが`IBonDriver::SetChannel`に渡すチャンネルのインデックス、つまりChSetファイルの`channel id`です。
「チューナ空間」もChSetの`space id`なので、ch2と同じ計算で番号を振っています。

EDCBは`<BonDriver名>(<チューナ名>).ChSet4.txt`を探し、見つからなければ`<BonDriver名>().ChSet4.txt`を読みます。
スキャンではどちらの名前も分からないので、括弧の中は空にします。
必要に応じて名前を変えてください。
`ChSet5.txt`は、Settingフォルダーに1つ置きます。

文字コードはBOM付きUTF-8です。
EDCBは先頭がBOMならUTF-8、そうでなければ実行環境のコードページとして読むので、確実に読ませるにはBOMが必要です（EDCB自身もBOM付きで書きます）。
改行はCRLFで、見出し行はありません。

「リモコンID」列には、放送が実際に書いている値だけを書きます。
この列は1バイトで、中身はARIBの`remote_control_key_id`です。
ch2の「リモコン番号」はTVTestが「チャンネル番号」として扱う別のもので、110度CSでは3桁のサービスIDが入ります。
そのままEDCBに持っていくと切り捨てられます（310は54になります）。
EDCBに付いている変換スクリプトはch2の値をそのまま使うのでこの問題が起きますが、coaxは地上波のTS情報記述子とTLVのリモコンキー記述子から取れた値だけを書き、それ以外は0にします。

ネットワーク名はNITから取ります。
変換スクリプトは、ch2にネットワーク名の欄が無いのでチャンネル名で代用しますが、スキャンではネットワーク名記述子を読むので、実際のネットワーク名を書けます。

ネットワーク名とリモコンIDは、どちらもNITが取れて初めて分かります。
TLVでは同じTLV-NIT第1ループの隣り合った記述子なので、基本的には片方が無いときはもう片方もありません。
衛星の既定の上限22秒は、これを見込んだ値です（[スキャンの解析時間](scan.md#スキャンの解析時間)）。
取れなかった場合、ネットワーク名は空欄、リモコンIDは0になります。
どちらもEDCBでは表示と並べ替えにしか使わないので、動作には影響しません。

ワンセグ（部分受信）のサービスは入れません。
coaxはテレビのサービスだけを書き出すので、「部分受信か」列は常に0です。
変換スクリプトの既定（`savePartial = False`）と同じ扱いです。

書けなかったチャンネルは、理由と一緒に標準エラー出力に出します。

## オプション一覧

`coax export`では、`--input PATH`、`--output PATH`、`--format mirakurun|dvbv5|chset|ch2|chset4|chset5`、`--route NAME`、`--channel-name scanned|transponder`、`--service-id`、`--tsmf-rel-ts`、`--lnbf NAME`、`--sat-number N`を指定できます。

`--lnbf`と`--sat-number`は`dvbv5`だけで使えます（Mirakurunのチャンネル一覧では選局するコマンドに任せ、ChSetにはLNBやDiSEqCを書く列がないためです）。

`--route`は形式によって意味が違います。
Mirakurun形式では書き出す値そのもの（`scanned`ならスキャンが記録した値）です。
`dvbv5`ではどの線のファイルを書くかで、省略すると、スキャンが記録した線ごとにすべて書きます。
