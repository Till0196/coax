# チューナーホスト（`coaxd`）

`coaxd`は、チューナーを一括して管理し、選局、TSの出力、内蔵カードリーダーへのアクセスを提供するデーモンです。
対象は、USBで直接制御するチューナー、Linux DVB、px4_drvやEarthsoftのドライバー、Windows BDAのチューナーで、HTTPとPC/SCで提供します。
Mirakurunなどの上位のソフトウェアから、チューナーとして使われることを主な目的にしています。

この文書はプロトコルと動作の仕様です。
実装と食い違っている場合は、どちらかの不具合です。
チャンネル定義プロパティの意味は[channel-files.md](channel-files.md)にあります。

## プロセスモデル

USBチューナーはインタフェース0を排他的にclaimします（Linuxのusbfs `USBDEVFS_CLAIMINTERFACE`、macOSのIOKit `USBInterfaceOpen`、WindowsはWinUSBのハンドルを共有なしで開くこと）。
1台のデバイスの全チューナーのTSが1本のバルクエンドポイントで多重化され、チューナー制御もスマートカードのUARTも同じ経路を共有します。
したがって、1台のデバイスを扱えるプロセスは常に1つです。
Linux DVBのフロントエンドとWindows BDAのフィルタグラフも排他的に使われる点は同じ（使用中のfrontendは`EBUSY`、1つのBDAチューナーに2つのグラフは組めない）なので、同じプールで管理して同じように割り当てます。
所有者プロセスを置くのはこの制約のためで、設計で回避できるものではありません。

- 2バイナリ構成。所有者デーモン`coaxd`と、それを呼ぶCLI`coax`
- `coax`は接続に失敗すると`coaxd`を起動します（detach起動）。起動完了の判定はプロセス生成ではなく実際に接続できたことで行い、50ms間隔、最大10秒でポーリングして最後に`/version`が応答することを確認します
- `coaxd`の探索順は環境変数`COAXD`、`coax`実行ファイルと同じディレクトリ、`PATH`
- 多重起動を防ぐため、ハードウェアにアクセスする前にロックを取得します（Linux、macOSはソケットと同じディレクトリの`http.sock.lock`への`flock`、Windowsは利用者のSIDを含む名前付きミューテックス。[os.md](../setup/os.md)）。どちらもプロセスが終了するとカーネルが解放します。異常終了したデーモンが残したソケットは、接続を試して応答が無いことを確認してから削除します
- アイドル終了：接続数が0の状態が3回続いたら終了します。既定は合計15秒（5秒間隔×3回）。数えるのはUnixソケット、`--http`のTCP、PC/SCソケットの合計で、どれか1つでも接続があれば終了しません。ネットワーク越しに常用する場合は`--idle 0`で常駐させてください
- 録画や視聴のクライアントは接続を維持するので、使用中にデーモンが終了することはありません

次の機能は持ちません。
BonDriver互換層、録画予約などのフロントエンドの機能、TSの内容を加工する処理です。
TSを外部のプログラムに通すときは、`coax pcsc`が作成するPC/SCソケットでカードをそのプログラムに提供します。

### ソケットの位置

| 環境 | ディレクトリ | 権限 |
| --- | --- | --- |
| Linux（root）| `/run/coaxd` | ディレクトリ0755 / ソケット0666 |
| Linux（一般ユーザー）| `$XDG_RUNTIME_DIR/coaxd`、無ければ`$TMPDIR/coaxd-$UID` | 0700 / 0600 |
| macOS | `$TMPDIR/coaxd` | 0700 / 0600 |
| Windows | `%LOCALAPPDATA%\coaxd` | ACL継承（`chmod`はしません）|

ファイル名は`http.sock`。
デーモンが開くソケットはこの1つだけです（`pcscd.comm`は`coax pcsc`が同じディレクトリに作成します）。
Unixソケットのパス長には上限があり（Linux、Windows 108バイト、macOS 104バイト）、超えると`connect`が`EINVAL`を返すだけで原因が分からないので、`coax`と`coaxd`はどちらも使う前に長さを検査し、理由付きのエラーにします。

## プロトコル

制御もTSもHTTP/1.1です。
既定はUnixドメインソケット（Windows含む）、`--http 127.0.0.1:PORT`を明示したときだけTCPも開きます（mpv/VLCはUnixソケットを開けないため）。
非ループバックへのbindは`--allow-remote`が無ければ拒否します。

どの待ち受け先でも、提供するエンドポイントは同じです。
設定できるのは、TCPのポートを開くかどうかと、ループバック以外に公開するかどうかだけで、それぞれ`--http`と`--allow-remote`で指定します。

TCPのポートは、Webページからの要求を受け付けません。
同じマシンのブラウザーで開いたページも、`127.0.0.1`へ要求を送れるためです。

- `Origin`ヘッダーの付いた要求と、`Sec-Fetch-Site`が`none`以外の要求は403で拒否します。アドレスを直接開いた要求（`none`）は受け付けます
- `--allow-remote`が無いときは、`Host`がループバックのアドレスか`localhost`の要求だけを受け付けます（DNSリバインディング対策）
- カードへ本文を送る`POST`（`session`・`transmit`）は、`Content-Type: application/json`でなければ415で拒否します

### アクセスできる範囲

デーモンは、要求元を区別しません。
ソケットかポートにアクセスできれば、誰でもチューナーとカードを使え、`X-Coax-Priority`で他の接続のチューナーを奪えます。
アクセスできる範囲は、ソケットの権限とポートの公開範囲だけで決まります。

- 一般ユーザーで動かすと、ソケットはそのユーザー専用のディレクトリに作られ、他のユーザーはアクセスできません
- rootで動かすと`/run/coaxd/http.sock`は0666になり、そのマシンの全ユーザーが使えます。チューナーを共有するための設定です
- `COAXD_SOCKET_DIR`（`--socket-dir`）を指定すると、一般ユーザーでもソケットは0666になります。アクセス範囲はディレクトリの権限で制御してください
- Windowsでは、ソケットの権限を`%LOCALAPPDATA%`から継承します
- `--allow-remote`を付けると、ポートにアクセスできるネットワーク上の誰でも使えます

USBの受け渡し用のソケット（`--usb-socket`）は、HTTPのソケットの権限によらず0600で、デーモンと同じユーザーだけが使えます。

ソケットのディレクトリが一時ディレクトリにあるとき（`$XDG_RUNTIME_DIR`の無いLinuxなど）、デーモンと`coax`は、ディレクトリの所有者が自身かrootで、他のユーザーが書き込めないことを確認してから使います。
他のユーザーが先に作成していた場合は、起動も接続もしません。

### 状態を持たない

設計の原則は、状態を持たないことです。
- サーバーが持つクライアント状態は開いている接続だけ。セッションID、lease ID、予約は一切ありません
- チューナーの占有はその接続が生きている間だけです
- 状態を問い合わせるエンドポイントはその時点のスナップショットを返すだけで、何度呼んでも状態は変わりません

## エンドポイント

| メソッドとパス | 内容 |
| --- | --- |
| `GET /version` | `version`（デーモン自身のバージョン）、`commit`、`started`（起動時刻。RFC3339のUTC）、`arch`（ビルドの CPU。`GOARCH` の綴りで `amd64`・`arm64`）。OpenAPI文書の`info.version`（`1.0.0`）とは別物です |
| `GET /tuners` | チューナー一覧。デバイスは開かない（後述）|
| `GET /tuners?open=1` | 各デバイスを実際に開いて構成を確定させる |
| `GET /tuners/{id}` | 1チューナーの詳細。ストリーム中でも呼べる |
| `GET /tune?…` | 選局してロックを待ち、結果をJSONで返す。TSは返さない（スキャン用）|
| `GET /stream?…` | 選局してTSを`video/mp2t`のchunkedで送る。主な用途 |
| `GET /cards` | カードスロット一覧 |
| `GET /cards/{id}?probe=1` | カードの有無を実際に確認する |
| `POST /cards/{id}/session` | 1回のリセットと続くAPDU群。PC/SCを使わないクライアント向けの一括操作 |
| `POST /cards/{id}/connect` | カードを開き、このHTTP接続で保持する |
| `DELETE /cards/{id}/connect` | 開いたカードを解放する |
| `POST /cards/{id}/transmit` | 保持しているカードにAPDUを1本送る |
| `POST /cards/{id}/transaction` | カードを共有している他の接続に対して占有する |
| `DELETE /cards/{id}/transaction` | 占有を解除する |
| `GET /cards/{id}/events?since=N&wait=S` | スロットのイベント数が`N`から変わるまで待つ（long poll）|
| `GET /openapi.json` | このインタフェースの記述（OpenAPI 3.1）|

機械で読める正式な記述は`GET /openapi.json`です。
内容は`internal/coaxd/host/hostapi/swagger.json`にコミットしてあり、デーモンはそれを埋め込んで返します（外部への依存はありません）。
手書きではなく、ハンドラと`hostapi`の型から生成しています。
再生成は`go generate ./internal/coaxd/host/server/`で行います。
再生成を忘れると、`internal/coaxd/host/server/openapi_test.go`がルーティングテーブル、受け付けるパラメーター、応答の型のすべてのフィールドと照合して、テストを失敗させます。

### カードの所有者

`/connect`で開いたカードは、そのリクエストを送ったHTTP接続に属します。
接続が閉じると（閉じ方によらず）解放されます。
チューナーのleaseと同じ規則で、セッションIDも期限切れの処理もありません。
異常終了したクライアントのカードも、ソケットが閉じることで解放されます。

1つの接続が1つのセッションです。
2枚を同時に開くクライアントは、接続を2本使います。
トランザクションも同じ接続に属するので、カードを占有したまま異常終了したクライアントが占有し続けることもありません。

`session`は、リセットとAPDU群を一括で実行する操作です。
状態を持たないクライアント（`coax card`や、1往復で済む用途）はこちらを使います。
次に送るAPDUが前の応答で決まるやり取りは、`session`では実行できません。
リクエストを分けると毎回リセットが入り、リセット以降にカードが保持している状態が失われるためです。

### スロットの変化を待つ

`GET /cards/{id}/events?since=N&wait=S`は、スロットのイベント数が`N`から変わるまで応答を返しません。
`SCardGetStatusChange`に相当します。

ポーリングは、ハードウェアに近いデーモン側の1か所だけで行います。
`wait`の上限はデーモン側で30秒に固定していて、それより長い値を指定しても上限で返します。
待っている間だけデバイスを開くので、誰も監視していないスロットにはアクセスしません。
`wait=0`は待たずに現状を返します。

## クエリ文法

キーは、大文字か小文字かで意味が変わります。

- `^[A-Z][A-Z0-9_]*$`に一致するキーはDVBv5チャンネル定義プロパティ。値をそのまま渡します（[channel-files.md](channel-files.md)と同一の解釈）
- すべて小文字のキーは短縮名かホスト用のパラメーターで、下の表にあるものだけです。表に無い小文字のキーは`400 invalid_parameter`にし、無視はしません
- 短縮名と大文字形の併用は`400`です

`system`（`DELIVERY_SYSTEM`）と`freq`（`FREQUENCY`）は必須で、どちらの表記でも指定できます。
無ければ`400`です。

| 短縮名 | 展開先 |
| --- | --- |
| `system` | `DELIVERY_SYSTEM` |
| `freq` | `FREQUENCY` |
| `stream_id` | `STREAM_ID` |
| `bandwidth_hz` | `BANDWIDTH_HZ` |
| `symbol_rate` | `SYMBOL_RATE` |
| `modulation` | `MODULATION` |
| `polarization` | `POLARIZATION` |
| `rolloff` | `ROLLOFF` |
| `gain` | `GAIN` |
| `lna` | `LNA` |

`gain`と`lna`は別のキーとしてクエリの解析を通りますが、[同じ設定](channel-files.md#gainとlna)なので両方指定すると選局の直前にエラーになります。

| ホスト用 | 内容 | 既定 |
| --- | --- | --- |
| `tuner` | チューナーIDの指定 | サーバーが空きから選ぶ |
| `lnb_power` | LNB給電。`VOLTAGE`プロパティになる | 給電しない |
| `lnbf` | アンテナのLNBf。`LNB`プロパティになる | 変換しない |
| `lock_timeout` | ロック待ち時間 | 5秒 |
| `settle` | ロック後にこの時間だけ待ってから再測定する | 2秒（`/stream`では常に0）|
| `begin` | `lock`（ロックしてからヘッダを返す）または`now` | `lock` |
| `bytes` | `/stream`専用。このバイト数を送ったら正常終了 | `0`（無制限）|
| `for` | `/stream`専用。最初の1バイトからこの時間で正常終了 | `0`（無制限）|
| `sync` | `/stream`専用。`on`／`off` | `on` |

`bytes`と`for`は両方指定でき、先に到達した方で終了します。
どちらも0なら終了条件の無いストリームで、クライアントが切断するまで送り続けます。
録画や視聴ではこちらを使います。

`settle`は、指定したときだけ再測定するものではありません。
`/tune`は既定の2秒で必ず再測定するので、往復は1回で済みます。
`/stream`では常に0です。
TSの送信を遅らせる理由が無いためです。

`lnb_power`と`lnbf`は別の設定です。
前者は同軸に給電するかどうか、後者はLNBfの種類、つまり局部発振周波数の選択です。
指定できる値とバックエンドごとの対応は[channel-files.md](channel-files.md#同軸ケーブルへの出力)にあります。
給電を切れないバックエンドに`lnb_power=off`を指定した場合は`409 unsupported`（`reason`は`lnb_supply`）を返します。
指定に反して給電することはありません。
クライアントから見れば「このチューナーでは対応できない」という応答なので、`out_of_range`と同じく、次のチューナーを試せます。
定義に無い値（`lnb_power=12`など）はクエリ解析の時点で`400 invalid_parameter`になり、チューナーを確保する前にエラーを返します。

チャンネルは周波数で指定します。
デーモンはチャンネルプランを持ちません。
日本のチャンネル名は`coax`が持っていて、`coax tune --ch 27`や`--ch BS01_1`を`FREQUENCY`に変換してから渡します。

選局に関係しない大文字キーは無視します。
チャンネル定義ファイルの1セクションには`SERVICE_ID`や`VIDEO_PID`のような選局に使わない行も含まれ、Linux DVBバックエンドは未知のプロパティを拒否するためです。
無視したキーは返します（`/stream`はヘッダ`X-Coax-Ignored`、`/tune`は`"ignored"`）。

## 優先度（`X-Coax-Priority`）

チューナーを確保する2つのエンドポイント（`/tune`と`/stream`）は`X-Coax-Priority`ヘッダを読みます。
値は整数で、指定が無ければ0です。
負の数も指定できます。

```
GET /stream?system=ISDBT&freq=557142857 HTTP/1.1
X-Coax-Priority: 10
```

規則は3つです。

1. 空きチューナーがある間は、どのストリームも止めません。優先度が効くのは、条件に合うチューナーがすべて使用中のときだけです
2. すべて使用中のときは、自分より小さい値で使っているクライアントからチューナーを奪います。奪う相手は、条件に合うものの中で最も小さい値のものです。止めるのが最も優先度の低い処理になるようにするためです
3. 同じ値どうしでは奪いません。先に確保したクライアントが使い続けます。ヘッダを送らないクライアントどうし（どちらも0）も同じです

チューナーを奪われた側のleaseは、デバイスが取り外されたときと同じように終了します。
contextがキャンセルされ、送信中のストリームのレスポンスがその時点で閉じます。
ボディの送信を始めた後でエラーを伝える方法はHTTPに無いので、通知はこれだけです。
奪ったクライアントの優先度は、`GET /tuners`の`priority`で分かります。

`tuner=`で1本を指定した要求も同じ規則で、候補が1つしかないだけです。
デバイスを開いている途中のチューナーは奪いません。
まだハンドルが無く閉じる対象が無いので、その要求には`503 tuner_busy`を返します（少し後に再度要求すれば、開き終わったleaseが対象になります）。

leaseを持ったまま同じチューナーを指定して選局し直すと、そのとき送った優先度がleaseの優先度になります。
視聴中に録画を始めたソフトウェアのように、途中で処理の重要度が変わるクライアントが、最初に送った値のまま扱われないためです。

数値として読めないヘッダは`400 invalid_parameter`にします。
0として扱うことはしません。
指定した値が反映されないと、そのクライアントは、本来優先されるはずの相手に録画を止められることになるためです。

`/stream`の応答には`X-Coax-Priority`が付き、そのストリームが最終的にどの優先度で保持されているかを示します。

`coax tune --priority`と`coax scan --priority`、BonDriver側の`[coax] Priority`がこのヘッダを送ります。
急がないスキャンには負の値が適しています。

## レスポンス

### `/tuners`

デバイスの配列です。
各デバイスは`name`、`naming`、`stable`、`backend`、`description`、`location`（bus/address）、`serial`、`port`、`deliveries`、`open`、`probed`、`probe_error`、`tuners`を持ちます。
`location`は`lsusb`と照合するために出力しますが、カーネルが再割り当てするので名前には含めません。

### `/tuners/{id}`

1チューナー分です。
常に含まれるのは`id`、`index`、`name`、`deliveries`、`leased`です。
`mode`（ボード全体で共有する復調器のモードなど）、`settings`（ドライバーから読んだ現在の設定）、`controls`（選局と一緒に設定できる項目）は、値があるときだけ含まれます。

`controls`はデバイスの種類から決まるので、デバイスを開く前から含まれます。
設定できる項目が無いチューナーには含まれません。
クライアントはこれを参照して、効かない設定項目を表示しないようにできます。

```jsonc
"controls": {
  // lnb_powerに指定できる値。offが無ければ給電を切れない。lowとhighの電圧（入切だけのデバイスは無し）。
  // sharedは給電線を他のチューナーと共有する単位（"board"か"card"）。
  "lnb":  {"levels": ["off","low","high"], "low": "11V", "high": "15V", "shared": "card"},
  // gain。"switch"は入切だけ（min／max／auto）、"steps"はdBの段（最も近い段に合わせる）。
  // deliveriesがあれば、その方式のときだけ効く（片側の入力にだけ増幅器があるデバイス）。
  "gain": {"kind": "steps", "decibels": [0, 1, 2, 3], "deliveries": ["ISDB-S"]}
}
```

汎用のBDA（`bda`）は給電も利得もドライバーが管理するので、`controls`は含まれません。
`priority`はチューナーが使用中のときだけ含まれます。
0も「優先度0で使用中」という意味なので、空きを0で表すことはできません。

`locked`、`status`、`cnr`、`strength`、`quality`、`dropped`、`stream`は、そのチューナーが使用中のときだけ含まれます。
読み取りにハードウェアへのアクセスが必要なためです。

### `/tune`

```jsonc
// 200 GET /tune?system=ISDBT&freq=557142857
{"tuner":"px4:ABC12345@1-2.1:2","backend":"px4","locked":false,"status":["SIGNAL"],
 "strength":-84.25,"elapsed_ms":5003,"ignored":["SERVICE_ID"]}
```

`tuner`、`backend`、`locked`、`elapsed_ms`は常に含まれます。
`status`、`cnr`、`strength`、`quality`、`ignored`、`relative_streams`は取得できたときだけです。
ロックしないことはエラーではありません。
スキャンは数百の周波数を調べ、その大半は空であることが前提で、空の周波数の信号強度も必要なためです。
`/stream`だけではスキャンを実装できないのはこのためで、「その周波数はこのチューナーの範囲外」を選局失敗と区別する必要もあります。

`relative_streams`は、そのチューナーのドライバーが衛星のストリームをトランスポンダ上の位置で指定する場合にだけ含まれます。
値はそのドライバーが持つTMCCテーブルの要素数（pt3ドライバーとpt1_drvなら8）です。
Stream IDをそのまま受け付けるチューナー（ほぼすべて）では省略されます。

これは名前ではなく数値で返します。
NITはストリームをStream IDで列挙しています。
そこから定義ファイルを組み立てるクライアントは、Stream IDを位置に置き換える必要があるかと、いくつの位置を調べればよいかを知る必要があり、その両方がこの1つの数値で分かります。
バックエンド名からは判断できません。
同じ`pt3`という名前が、Linuxでは相対番号しか受け付けないドライバーを、WindowsではStream IDをそのまま受け付けるcoaxdの実装を指すためです。

### `/stream`の応答ヘッダ

| ヘッダ | 内容 |
| --- | --- |
| `X-Coax-Tuner` | 実際に使われたチューナーのID |
| `X-Coax-Backend` | そのバックエンド名 |
| `X-Coax-Ignored` | 選局に使わなかったプロパティ名 |
| `X-Coax-Priority` | このストリームの優先度（[優先度](#優先度x-coax-priority)） |

## エラー

ストリームを始める前の失敗は、HTTPのステータスとJSONのボディ`{"error":{"code":…,"message":…,"reason":…}}`で返します。
選局まで進んでから失敗した場合は、それまでに測定できた値が`status`に含まれます（`/tune`の応答と同じ形式）。

| 状況 | ステータス | `code` |
| --- | --- | --- |
| パラメーター不正 | 400 | `invalid_parameter` |
| チューナーIDが存在しない | 404 | `unknown_tuner` |
| `/cards/{id}`のIDが存在しない | 404 | `unknown_tuner` |
| その方式を持たない／周波数が範囲外 | 409 | `unsupported`（`reason`は`delivery_system`か`out_of_range`）|
| LNB給電を要求どおりにできない | 409 | `unsupported`（`reason`は`lnb_supply`）|
| 利得を持たない／入切だけの増幅器にdBを指定した | 409 | `unsupported`（`reason`は`gain`）|
| そのデバイスにカードスロットが無い | 409 | `no_card_reader` |
| 時間内にロックしなかった（`/stream`のみ）| 502 | `no_lock` |
| ロックしたがTSになっていない | 502 | `no_sync`（[同期検査](#同期検査)）|
| 選局呼び出し自体が失敗 | 502 | `tune_failed` |
| カードが応答しない | 502 | `card_error` |
| USB切断 | 502 | `device_gone` |
| 空きチューナーなし／指名チューナー使用中 | 503 | `tuner_busy` |
| USBツリー自体が読めない | 503 | `no_devices` |
| ファームウェアファイルが無い | 503 | `no_firmware` |
| デバイスを開く権限が無い | 503 | `no_access` |
| デーモン側の不具合 | 500 | `internal` |

ロックしなかったときの扱いはエンドポイントによって異なります。
`/tune`は`200`で`"locked":false`を返します（スキャンでは正常な応答です）。
`/stream`は送るデータが無いので`502 no_lock`を返します。

トーンや偏波を出力できないハードウェアに要求した場合は`502 tune_failed`になります。
バックエンドが返す「トーンを出力できない」「電圧の段を選べない」は個別のコードに分類しておらず、メッセージにだけ理由が含まれます。

`no_devices`は「何も接続されていない」ではなく「バスにアクセスできない」という意味です（コンテナに`/dev/bus/usb`を渡していない等）。
何も接続されていないときは空の一覧を返します。

ストリーム開始後の異常（USBの切断など）は、接続を閉じることで通知します。
再試行はフロントエンドに任せ、ストリームの中にエラーの情報を含めることはしません。

## 同期検査

`/stream`は、ヘッダを返す前にストリームの先頭を読んで、TSとして成立しているかを検査します。
成立していなければ`502 no_sync`を返し、データを1バイトも送りません。

復調器だけでは、これを判断できないためです。
ロックは復調器の内部ループの状態に過ぎず、信号の無い同軸でも復調器はロックし、ノイズを出力し続けます。
CNRも値を返し、パケット数も増えます。
区別できるのはチューナーが出力するバイト列だけで、「同期バイト`0x47`が188バイト間隔で並んでいるか」で判定します。
給電が必要な配線で給電を忘れた場合もこの形で失敗するので、ここで検出します。

形式は伝送方式の名前ではなくバイト列から判別します。
`DELIVERY_SYSTEM=ISDBS`のチャンネルがTSを出力するかTLVを出力するかは名前からは決まらない（[ISDB-S3の書き方](channel-files.md#stream_id)）ので、先頭を両方の解析器に通し、先に同期が取れたほうを採用します。
`ISDBS3`を指定できるバックエンドでは、その指定をどちらを先に試すかの判断に使いますが、最終的な判定はバイト列で行います。

| | TS | TLV（ISDB-S3）|
| --- | --- | --- |
| 判定 | `0x47`が188バイト間隔で4つ並ぶ | `0x7f`＋既知の型で、書かれた長さの先にまた同じものが、4つ連続 |
| 偶然一致する確率 | `2^-24` | それ以下（型が5種しかないうえ、長さの先に次のヘッダがある必要がある）|

判定の確実さはTLVのほうが上です。
TSは「`0x47`の次は188バイト先」と仮定して検査しますが、TLVは次のヘッダの位置がヘッダに書かれています。

```
byte 0     0x7f
byte 1     '11' + packet_type(6bit)。0x01/0x02/0x03/0xfe/0xff の5種のみ
bytes 2-3  ペイロード長（ビッグエンディアン）
```

両方に通すコストは先頭の1回分だけで、どちらかが同期した時点でもう一方は破棄します（TSなら4パケット＝752バイト）。
形式を誤判定すると正常なTLV放送をノイズとして拒否するので、その損失のほうがはるかに大きくなります。

| 項目 | 値 |
| --- | --- |
| 打ち切り | 512KiBまたは3秒のどちらか早いほう |
| 成立時 | 読んだデータは破棄せず、そのままストリームの先頭として送る |
| 1バイトも受信しなかったとき | エラーにしない（「何も出力されない」は「別のデータが出力される」とは別の障害）|

検査を無効にするのは`sync=off`（`coax tune --no-sync`）だけです。
チューナーが実際に何を出力しているか確認するときに使います。

## 接続とチューナーの保持

スキャンは1本のチューナーで数百チャンネルを順に選局するので、呼び出しの合間に他のクライアントにチューナーを確保されると困ります。
セッションIDを持たずにこれを実現するため、leaseの所有者は接続そのものにしています。
`/tune`で確保したチューナーはリクエスト終了時には解放されず、接続が閉じたときに解放されます（`http.Server`の`ConnContext`/`ConnState`）。
`coax`側は1本のkeep-alive接続に固定しています（`MaxConnsPerHost: 1`）。

再利用されるのは明示的に指定されたチューナーだけです。
指定の無い要求が既存のleaseを再利用すると、1つの接続で2本録画するクライアントに同じチューナーを2度割り当てることになるためです。
`/tuners/{id}`はleaseではなく観測者として数えるので、ストリーム中でも応答できます。

### 終わりのあるストリーム（`bytes`/`for`）

leaseが接続に結びついているので、接続を切らずにストリームを止める手段が必要です。
終了条件の無いレスポンスを止める唯一の方法はボディを読み切らずに閉じることですが、Goの`http.Transport`は読み切っていないボディを閉じた接続を再利用せず破棄します。
つまり、ストリームを止めると接続が破棄され、leaseも解放されます。
スキャンは1チャンネルごとにサンプルを取得して止めるので、これでは毎チャンネルでチューナーを解放し、次のチャンネルではハードウェアの解放処理と競合することになります。

そのため`bytes`/`for`を指定できるようにしています。
サンプルを取得するクライアントは必要な量を指定し、サーバーがストリームを正常終了させます。
クライアントはボディをEOFまで読むので接続は維持され、leaseもチューナーもそのまま次のチャンネルへ引き継げます。
スキャン全体でチューナーを開くのは1回です。

### 解放中のチューナー

leaseの解放はハードウェアを閉じるところまでを含み、エンドポイントの停止と復調器のスリープはすぐには終わりません。
この間チューナーは`leases`に残したままにし、同じチューナーへの要求は解放の完了を待ちます（`handoverGrace`、5秒）。

待つのは解放中のチューナーだけです。
他の接続が使用中のチューナーには即座に`503 tuner_busy`を返します。
録画の終了まで待たせるより、すぐにエラーを返すほうが適切なためです。
相手より高い優先度を指定した場合にだけ、待たずに奪います（[優先度](#優先度x-coax-priority)）。

### 読み出しの止まったクライアント

ストリームを読まなくなったクライアントがチューナーを保持し続けないよう、TSの書き込み1回ごとに30秒のタイムアウトを設定します。
タイムアウトすると接続を閉じ、leaseを解放します。
奪われたleaseは、停滞している書き込みをその時点で中断します。
要求ヘッダーの読み込みにも10秒のタイムアウトがあります。
要求と要求の間で待機している接続にはタイムアウトを設定しません。
チューナーを保持したまま次の要求を待つのは通常の使い方だからです。

## ストリーム統計

`GET /tuners/{id}`は、そのチューナーがストリーム中なら`stream`を返します。
ストリームを開いていないチューナーではキー自体が含まれません（「0パケット受信した」と「0パケット破損していた」は正反対の意味なので、0で埋めると誤解を招きます）。

```json
{"stream":{"format":"ts","bytes":18800000,"packets":100000,"skipped":0,
           "sync_losses":0,"discontinuities":0,"nulls":12000,
           "errors":0,"scrambled":41200}}
```

`format`は`ts`か`tlv`で、どのフィールドに値が入るかを決めます。

| フィールド | 対象 | 意味 |
| --- | --- | --- |
| `bytes` | 共通 | チューナーが出力した全バイト数 |
| `packets` | 共通 | そのうちパケットとして認識できたもの（スタッフィング含む）|
| `skipped` | 共通 | パケットの一部でなかったバイト |
| `sync_losses` | 共通 | 同期が外れた回数（パケット数ではない。ノイズの塊は1回）|
| `discontinuities` | 共通 | 同じ系列の直前のパケットから連続していなかったパケット。TSはPIDごとの`continuity_counter`、TLVはMMTPのpacket_idごとの`packet_sequence_number` |
| `nulls` | 共通 | スタッフィング（TSはPID `0x1fff`、TLVは型`0xff`）|
| `errors` | TS | `transport_error_indicator`が立っていたパケット。復調器が訂正しきれなかったもの |
| `scrambled` | TS | `transport_scrambling_control`が0でないパケット。有料放送では0でないのが普通です |
| `control` | TLV | TLV-SI（多重の中身を記述する制御情報）|
| `ipv4`／`ipv6`／`compressed_ip` | TLV | 格納されたデータグラムの形式。日本のTLV多重はほぼすべて`compressed_ip` |
| `undecodable` | TLV | TLVとしては成立していたがMMTPヘッダを解析できなかったパケット |
| `forgotten` | TLV | シーケンステーブルが上限（4096系列）を超えて空にされた回数。通常は0で、0でなければ`discontinuities`の値は正確ではありません |

`discontinuities`はフロー（宛先アドレス＋ポート、または圧縮コンテキスト）ごとに数えます。
MMTPの`packet_id`はパッケージ内で一意ですが多重全体では一意ではないので、`packet_id`だけで数えると、別のフローが交互に現れるたびに誤検出します（16MBのISDB-S3の測定では、81件を誤検出しました）。
同じ理由で、番組と並行して送られるNTP（宛先ポート123）はMMTPとして解析しません。

TSでは`continuity_counter`の規則どおりに数えます。
ペイロードの無いパケットではカウンタは進まないので進んだら数え、重複パケット（同じカウンタの再送）は規格上許されるので数えず、アダプテーションフィールドの`discontinuity_indicator`が立っていれば送出側が意図した不連続なので数えません。
検出の精度もTLVのほうが上です。
TSの`continuity_counter`は4bitで16パケットごとに一周しますが、MMTPの`packet_sequence_number`は32bitなので実質一周しません。
TLVには`transport_error_indicator`に当たるものが無いので、ISDB-S3では電波が弱い状況も`errors`ではなく`discontinuities`に出ます。

いずれもストリームを開いてからの累計で、リセットされません。
レートが必要な場合は2回読んで差を取ります。

メモリ使用量は録画の長さに比例しません。
解析器が保持するのは、パケット境界までの端数バイトと、系列ごとの直前のカウンタだけです。

| | 保持するもの | 上限 |
| --- | --- | --- |
| TS | PIDごとのcontinuity_counter | `[8192]int8` = 8KiB固定（使っていないPIDも含む）|
| TLV | 系列ごとのMMTPシーケンス番号 | 4096系列を超えたらテーブルを空にして`forgotten`を数える |

測定値（1ストリームあたり）：正常なTS 560MBでヒープの変化なし、バッファは最大で1回の読み出し分。
ノイズ12MBでもバッファは1回の読み出し分＋探索範囲で上限に達します。
TLVは系列を意図的に20万件作ってもテーブルは4096件で止まります（上限が無い場合は10.9MBまで増えました）。

これらの値で、録画の失敗を3種類に切り分けられます。
録画ファイルではどれも同じに見えますが、対処はまったく異なります。

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `packets`が0のまま、または`sync_losses`が増え続ける | 受信できていない | アンテナ、`lnb_power` |
| `errors`が増える（TLVでは`dropped`を伴わない`discontinuities`）| 電波が弱い。復調器が訂正しきれていない | アンテナ、ブースター |
| `discontinuities`が`dropped`と一緒に増える | 読み出しが追いついていない。欠落は受信側で起きている | 書き込み先、CPU |

## チューナーID

`<バックエンド>:<識別子>:<チューナー番号>`。
識別子は次の優先順です。

1. OSが付けた名前：Linux DVBは`adapter0.frontend0`、キャラクタデバイスは`px4video0`、`pt3video0`、`pt1video0`、Windows BDAはデバイスパスのFNV-1a 64ハッシュ。USB以外はこれ
2. シリアル番号：デバイスを開かずにOSから取得できるもの（LinuxとmacOS。WindowsはSetupAPIからデバイスを開かずに読める項目に無いため使いません）
3. `シリアル@ポート経路`：1台が複数のUSBデバイスとして認識されてシリアル番号を共有するデバイス（`px4`、`pxmlt`）は、もう一方が接続されていなくても常にこの形式です
4. `p<ポート経路>`：ルートハブからの物理経路（`p1-2.3`）。macOS/Windowsでは通常こちら
5. `u<bus>-<address>`：ほかに識別子が無い場合。再接続で変わるので、一覧に`"stable": false`を付けて明示します

## 一覧の作り方

`GET /tuners`はデバイスを開きません。
開くと電源が入り、デバイスによってはファームウェアが書き込まれます。
接続されたデバイスの一覧を取得するだけでそれが起きるのは不適切なので、各バックエンドが持つデバイスの情報から構成を返し、`"probed": false`を付けます。
`?open=1`のときだけ実際に開いて`"probed": true`にします。

例外はLinux DVBとpx4_drvのキャラクタデバイスで、こちらはデバイスを短時間だけ開いて情報を取得します。
デバイスツリーにその情報が無いためです（DVBは名前と方式を`FE_GET_INFO`と`DTV_ENUM_DELSYS`で、`chardev`は`PTX_SET_SYSTEM_MODE`にISDB-TとISDB-Sを順に渡し、受け付けられたほうを方式とします）。
pt3ドライバーとpt1_drvのノードは名前から方式が分かるので開きません。
使用中で開けなくても、一覧からは削除しません。
録画中のチューナーが一覧から消えるほうが問題になるためです。

`?open=1`で開けなかったデバイスは`"probe_error"`にその理由が入ります（ファームウェアが無い、権限が無い、他のプロセスが使用中、など）。
ただし1プロセスしか開けない排他的なデバイスは、`?open=1`でも開かずにスキップし、`probe_error`も付きません。
開くこと自体が他の録画を妨げるおそれがあるためで、「確認できなかったことは報告する」という原則の唯一の例外です。

`deliveries`（受信できる方式）は、USBバックエンドでは確実な情報ですが、`dvb`ではドライバーが列挙に応じないことがあり、`bda`には取得する手段がありません。
空欄は「不明」であって「無い」ではなく、方式を指定した要求でも候補として選ばれます。
対応していなければ、選局の時点でエラーになります。

方式名の表記違いは同じものとして扱い、一覧には両方の表記を含めます。
`DVB-C`と`DVB-C/ANNEX_A`、`ISDB-C`と`DVB-C/ANNEX_C`は同じ方式です。
クライアントは名前で照合するので、片方しか含めないと、受信できるのに非対応と判定されることになります。
Annex Bだけは別の方式なので同一視しません。

## 内部構造

```
coaxd
  ├ HTTPリスナー（Unixソケット、任意でTCP）
  ├ PC/SCリスナー（pcsc-lite互換、同居）
  └ Supervisor（列挙・ホットプラグ）
      └ デバイスアクター（1デバイス=1所有権、ハンドルを所有）
          ├ チューナー割り当て（接続に1:1のlease）
          ├ TS demux → チューナー別リングバッファ
          └ カード保持（winscard/usbcard）
```

- アクターが直列化するのは所有権の管理だけです。デバイスを開く、チューナーを割り当てる、カードを保持する、参照カウントを増減する、lingerを計る、最後に閉じる。どれもすぐ終わる処理です
- I/Oは直列化しません。`Stream.Read`、`Tune`、`Status`、カードとの通信は、呼び出し元がそのまま実行します。下位のドライバーがすでに必要な粒度でロックを持っており、その前にもう1つ待ち行列を置くと、秒単位でかかるカードのリセットの間、信号強度の読み出しが待たされます
- 例外はWindows BDAだけです。COMを呼ぶスレッドはCoInitializeEx済みでなければならない一方、デーモン内の処理は任意のタイミングで別のOSスレッドへ移ります。そのためBDAデバイスは専用のスレッドを1本固定し、COM呼び出しをすべてそのスレッドで実行します。ストリームの読み出しはファイルI/Oなので対象外です
- 参照カウントは用途別に分けます。lease（ストリーム）、カード、観測者の3つです。最初の1つを特別扱いする構造にはしません
- 最後の利用者がいなくなっても即座には閉じません（linger、既定10秒）。`px4`系のオープンはファームウェアの書き込みを伴う秒単位の処理で、カードの有無を確認するポーリングは400msごとに開閉するためです。アイドル終了とSIGTERMのときはlingerを待たずに閉じます
- バッファが溢れたらデータを破棄します。遅いクライアントのためにUSBの読み出しを止めると、同じエンドポイントを共有する他のチューナーも止まるためです。破棄した数は`/tuners/{id}`の`dropped`に表示されます
- 書き出しは、一定量まで溜めてからまとめて行います。188バイトごとにクライアントを起こすことはしません
- 選局の直後は、必ずバッファを空にしてから送信を始めます（前のチャンネルのデータを出力しないため）

## ホットプラグ

- 取り外しの検出は主にI/Oエラーで行い、補助としてリクエストのたびに再列挙します。netlink ueventには対応していません
- 対象のI/Oエラーは`usbio.ErrGone`（ENODEV / ENXIO / ESHUTDOWN / ESRCH、WindowsのERROR_DEVICE_NOT_CONNECTED、macOSのkIOReturnNoDevice）です。ESRCHは「no such process」と表示されるので無関係に見えますが、usbfsは、claimしていたインタフェースが消えたエンドポイントへの転送をこのエラーで拒否します。実機で確認しています
- チューナーの使用中にこのエラーが出たら、そのデバイスは即座に破棄されます（leaseはcancel、ハンドルは閉じる）。バス上にまだ見えていても再利用しません
- 取り外されたとき：そのデバイスのすべてのストリームを閉じ（クライアントにはEOF）、カードの保持を解放し、ハンドルを閉じます。ストリームを継続しているように見せることはしません
- 再接続されたとき：新しいデバイスとして初期化し直します。同じシリアル番号なら同じIDになりますが、名前が同じでもデバイスの同一性は毎回検証します
- フロントエンドから見た復旧は、同じURLで再試行すれば再開できる、というものです。それ以上の自動復旧は行いません

## Mirakurunとの接続

`tuners.yml`の`command:`に`coax tune`を書きます。
`coax tune`は、`coaxd`に接続して（起動していなければ起動して）クエリを組み立て、レスポンスのボディを標準出力に書き出すだけのコマンドです。

```yaml
- name: SAMPLE-T1
  types: [GR]
  command: coax tune --system ISDBT --ch <channel>
  decoder: ts-filter
```

MirakurunはSIGTERMで止めるので、`coax tune`はSIGTERMで接続を閉じて終了します（それだけでチューナーが解放されます）。

`decoder`にはTSを通す外部のプログラムを書きます（ここでは`ts-filter`）。
そのプログラムにPC/SCソケットのパスを渡す必要があります。
`tuners.yml`にはチューナー別の環境変数の設定が無いので、Mirakurunのプロセス全体に`PCSCLITE_CSOCK_NAME`を渡すのが確実です（systemdなら`Environment=`）。

## コマンドラインオプション

`coaxd [options]`。
位置引数は取りません。

| フラグ | 内容 | 既定 |
| --- | --- | --- |
| `--socket-dir` | ソケットを置くディレクトリ | ユーザーごとのランタイムディレクトリ |
| `--socket` | HTTPソケットのパス | `--socket-dir`の中の`http.sock` |
| `--http` | 追加で待ち受ける`host:port` | 開かない |
| `--allow-remote` | `--http`にループバック以外を許す | 不許可 |
| `--firmware-dir` | ファームウェアの置き場所 | OSごとの既定 |
| `--dvb-root` | Linux DVBのデバイスノードの場所。他OSでは無視 | `/dev/dvb` |
| `--chardev-root` | px4_drv、pt3のキャラクタデバイスの場所。他OSでは無視 | `/dev` |
| `--board-linger` | 最後の利用者がいなくなってからデバイスを開いておく時間。`0`ですぐに閉じる | 10秒 |
| `--idle` | 合計この時間だけ使われなければ終了。`0`で常駐 | 15秒 |
| `--quiet` | エラー以外を出力しない | 出力する |
| `--log` | 診断用のログをこのファイルに追記する（デーモンの出力、クライアントに返したエラー、デバイスの動作）| 環境変数`COAXD_LOG`、無ければ書かない |
| `--usb-socket` | USBデバイスのファイルディスクリプターを受け取るソケット。バスに直接アクセスできないAndroidなどの環境向け | 開かない |
| `--version` | ビルドの情報を出力して終了する（デバイスにはアクセスしません）| - |
| `--tray` | 通知領域にアイコンを出す（ある環境で）。`--tray=false`で出さない | 出す |

`--idle`が間隔ではなく合計時間なのは、設定するときに考えるのは合計時間だからです。
何回に分けて確認するかは実装上の事情なので、3回に固定しています。
常用するマシンでは、systemdの`PartOf=mirakurun.service`等で`--idle 0`の常駐にする想定です。

サブコマンドは1つだけあります。
`coaxd load-asv52xx-firmware`（別名`load-px3-firmware`）は、ファームウェアが書き込まれていないPX-S3U系デバイスにファームウェアを書き込んで起動します。
`coaxd help`で使い方を表示します。
