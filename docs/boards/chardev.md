# ptxキャラクタデバイス経由のチューナー（バックエンド`chardev`）

| | |
| --- | --- |
| バックエンド | `chardev`（ドライバーはpx4_drv、pt3ドライバー、pt1_drvの3つ）|
| 対応OS | Linux専用（WindowsのPT1/PT2/PT3は[earthsoft-windows.md](earthsoft-windows.md)）|
| 伝送方式 | ISDB-T、ISDB-S（ptx ioctlにはこの2つしかありません）|
| ファームウェア | 不要（必要なデバイスではドライバー側が持ちます）|

recpt1が使う「ptx」ioctlを持つキャラクタデバイスのドライバーを通して、チューナーを使います。
対象のドライバーは次の3つです。
[px4_drv](https://github.com/nns779/px4_drv)、[pt3ドライバー](https://github.com/m-tsudo/pt3)、pt1_drv（[stz2012/recpt1](https://github.com/stz2012/recpt1)の`driver/`などに同梱）。
3つとも、ioctlの番号も、`FREQUENCY`構造体の大きさも、チャンネル番号の振り方（UHF 13chがどれも63番）も同じです。
そのため実装は`internal/coaxd/chardev`の1つにまとめてあり、ドライバーごとに違うのは受信できる範囲と選局の細かいところだけです。

3つのドライバーを1つのバックエンドで扱います。
どれも「ドライバーが作ったキャラクタデバイスを1つのプロセスが開き、ptx ioctlで制御する」という同じ使い方だからです。
`/tuners`には`chardev:px4video0:0`、`chardev:pt3video0:0`、`chardev:pt1video0:0`のように並びます。
どのドライバーのノードかは、ノードの名前で判別します（ドライバーごとに名前の接頭辞が決まっているので、開かずに判別できます）。

ドライバーの違いのうち、クライアントに関係するものはAPIで取得できます。
たとえば`STREAM_ID`が相対番号か識別子かは`GET /tune`の`relative_streams`で分かるので、クライアントはドライバーの種類を区別する必要がありません（[下記](#stream_idの解釈)）。

この文書は、共通の動作を先に、ドライバーごとの違いを後に書いています。

## 対応ドライバーとノード

| ドライバー | ノード | 対象ハードウェア |
| --- | --- | --- |
| px4_drv | `/dev/px4video*`、`/dev/pxmlt5video*`、`/dev/pxmlt8video*`、`/dev/isdb2056video*`、`/dev/isdb6014video*`、`/dev/pxm1urvideo*`、`/dev/pxs1urvideo*`、`/dev/isdbt2071video*` | PLEX PX-W3U4 / Q3U4 / W3PE4 / Q3PE4 / W3PE5 / Q3PE5 / MLT5U / MLT5PE / MLT8PE / M1UR / S1UR、DigiBest ISDB2056 / ISDB6014 / ISDBT2071 |
| pt3ドライバー | `/dev/pt3video0`〜`3`（`video0`/`1`がISDB-S、`video2`/`3`がISDB-T）| Earthsoft PT3 |
| pt1_drv | `/dev/pt1video0`〜`3`（並びは同上）| Earthsoft PT1（PCI ID `10ee:211a`）/ PT2（`10ee:222a`）|

ノード1つが1チューナーです。
PT3とPT1/PT2では、どのノードが衛星か地上かはドライバーが決めていて、変えられません。
2枚目のボードは`pt3video4`〜`7`（PT1/PT2も同じ）と、4つずつ続きます。
番号はPCIスロットの順ではなく、認識された順です。

pt3ドライバーだけは、3つに共通するptx ioctlのほかに`GET_STATUS`などの独自のioctlを持ちます。

pt1_drvは、1つのドライバーでPT1とPT2の両方を扱います。
2つのボードの違いは復調器のクロック（20 / 25MHz）とメモリインタフェースの調整回数（128 / 166回）だけで、ノードの数も並びも同じなので、coaxでも同じに扱います。

### 一覧の作り方

pt3ドライバーとpt1_drvのノードは、名前から伝送方式が分かるので、`/tuners`では開きません。

px4_drvのノードは、一度だけ開いて伝送方式を確認します（`PTX_SET_SYSTEM_MODE`にISDB-TとISDB-Sを順に渡し、受け付けられたほうをその方式とします）。
px4_drvは最初の`open()`でチューナー基板の電源を入れ、最後の`close()`で切るので、一覧のたびに全ノードを開くと、そのたびに電源が入り直します。
そのため確認した結果はキャッシュし、実際にチューナーを開いたときに確認し直します。

どのドライバーも、1つのノードを同時に1つのプロセスからしか開けません（px4_drvは2つめの`open()`に`EALREADY`を返します）。
これはDVBフロントエンドの`EBUSY`と同じ排他なので、DVBアダプターやWindows BDAと同じように貸し出します。

## 前提

ドライバーが入っていて、モジュールが読み込まれていれば使えます。
ファームウェアのファイルは不要です（px4_drvは、IT930xへのファームウェアの書き込みをドライバー自身が行います）。

ノードの権限は、各ドライバーに付いているudevルールが設定します。
どのドライバーでも、ノードは`video`グループのものになります。
権限は、px4_drvの`etc/99-px4video.rules`が`0664`、pt3ドライバーの`etc/99-pt3.rules`とpt1_drvの`etc/99-pt1.rules`が`0666`です。
`coaxd`を動かすユーザーが`video`グループに入っていれば、基本的にはほかの設定は不要です。

ノードが`/dev`に無い環境（コンテナなど）では、`--chardev-root`で場所を指定します。
3つのドライバーのどれにも効きます。

### モジュールパラメーター（LNB給電をどこで決めるか）

pt3ドライバーは`lnb`と`lnb_force`の2つを持ちます。
`lnb`は電圧（`0`:OFF／`1`:+11V／`2`:+15V）、`lnb_force`はそれを常に出すかどうかです。
給電をチャンネルごとに決めるか、同軸に常に流しておくかの選択で、どちらがよいかは設備によります。

| | `lnb_force=0`（既定）| `lnb_force=1` |
| --- | --- | --- |
| 給電が入るとき | ISDB-Sの選局時。チューナーを閉じると切れる | モジュールの読み込み時。以後は常に給電 |
| 電圧を決めるもの | チャンネルの`VOLTAGE`（省略時は給電なし）| モジュールパラメーターの`lnb` |
| `coaxd`の`VOLTAGE`／`--lnb-power` | 有効 | 無効（後述）|

同軸に常に給電しておきたいとき（同じ同軸にほかの機器もつながっている、選局のたびに給電が入り切りするのを避けたい、録画していない間もLNBを動かしておきたい）は、`lnb_force=1`と、`lnb=1`（11V）または`lnb=2`（15V）を設定します。
`coaxd`の既定は「給電しない」なので、常時給電はこの設定で行います。

ただしこのとき、`coaxd`からの給電の指定は無効です。
`lnb_force=1`では、`LNB_ENABLE`も`LNB_DISABLE`も何もせずに成功を返すので（`pt3_pci.c`の`if (count <= 1 && !lnb_force)`）、`coaxd`は指定が無視されたことを検出できません。
チャンネルに`VOLTAGE = high`と書いても、電圧は`lnb`で決めた値のままです。
エラーにもならないので、給電の設定はどちらか一方にそろえてください。

| やりたいこと | 設定 |
| --- | --- |
| 同軸に常に給電する | `lnb_force=1`にして、`lnb`で電圧を指定。定義ファイルに`VOLTAGE`は書かない（書いても無効）|
| チャンネルごとに給電を決める | `lnb_force=0`のまま（既定）。電圧は`VOLTAGE`で指定する |

どちらを選んでも、電源挿入器やブースターがすでに給電している同軸にさらに給電すると、機材が壊れます。
`lnb_force=1`はモジュールを読み込んだ時点で給電するので、同軸の状態を確かめてから設定してください。

pt1_drvにも既定の電圧を決める`lnb`があります。
`lnb_force`はありません。

## 定義ファイル

共通の書式は[channel-files.md](../reference/channel-files.md)にあります。
3つのドライバーとも、見る項目は同じです。

| キー | 意味 |
| --- | --- |
| `DELIVERY_SYSTEM` | `ISDB-T`または`ISDB-S` |
| `FREQUENCY` | 地上波はHz、衛星は第1中間周波数のkHz |
| `STREAM_ID` | ISDB-Sのみ。解釈がドライバーごとに違います（[下記](#stream_idの解釈)）。省略すると相対スロット0 |
| `VOLTAGE` | ISDB-SのLNB給電。`off`／`low`（11V）／`high`（15V）。省略すると給電しない |

ioctlの`PTX_SET_CHANNEL`が受け取るのは、周波数ではなくドライバーの中のチャンネル番号です。
そのため`coaxd`が周波数をチャンネル番号に直して渡します。
変換できるのはドライバーのテーブルにある周波数だけで、それ以外は`unsupported` / `out_of_range`を返します。

### 受信できる範囲

| | px4_drv | pt3ドライバー | pt1_drv |
| --- | --- | --- | --- |
| 地上波 | VHF 1〜12、CATV C13〜C63、UHF 13〜62（93.143〜767.143 MHz、6 MHz間隔で切れ目なし）| VHF 1〜12、CATV C13〜C63、UHF 13〜61（93.143〜761.143 MHz）| VHF 1〜12、CATV C13〜C63、UHF 13〜62（93.143〜767.143 MHz）|
| 衛星 BS | 12波（1049480 kHzから38360 kHz間隔）| 同左 | 同左 |
| 衛星 CS | ND02〜ND24の12波（1613000 kHzから40000 kHz間隔）| 同左 | 同左＋ND01〜ND23の奇数12波（1593000 kHzから40000 kHz間隔）|

- pt3ドライバーがUHF 62chを受信できないのは、周波数を112個のテーブルで持っているためです。pt1_drvは計算で求めるので受信できます。
- CSの奇数トランスポンダ（ND01〜ND23）を持つのはpt1_drvだけです。pt3ドライバーにもpx4_drvにもありません。
- pt1_drvは、衛星のチャンネルを周波数ではなくPLLに書く値そのもので持っています。36個のうち35個は「16384＋中間周波数(MHz)」ちょうどです。残る1つはBS-1で、この値だけが並びから外れていて（バンドの値も隣と違います）、意味は分かっていません。BS-1を0番とするのはrecpt1のチャンネルテーブルのとおりで、coaxの対応もそれに合わせています。

### 周波数の刻みと`slot`

ISDB-Tのキャリアは、チャンネルの中心から1/7MHzずれた位置にあります。
このずれの扱いがドライバーごとに違います。

- px4_drv：ずれを`slot`（kHz単位の補正値）に入れて渡します。定義ファイルの`473142857`はkHzに丸めて473143kHzとなり、ドライバーのテーブルどおりの周波数になります。
- pt3ドライバー：地上波では`slot`を見ません。補正できないので、定義ファイルの周波数はチャンネルの中心から±3MHz以内でなければなりません。
- pt1_drv：地上波でも`slot`を見ますが、単位がMHzです。チャンネル間隔が6MHzなので補正に使える細かさが無く、0を渡します。周波数の条件はpt3ドライバーと同じです。

### `STREAM_ID`の解釈

これが3つのドライバーの最も大きな違いです。

| ドライバー | 12未満 | 12以上 | `relative_streams` |
| --- | --- | --- | --- |
| px4_drv | TMCCの相対スロット番号 | TSID（そのTSIDのストリームを探す）| 0（返さない）|
| pt3ドライバー、pt1_drv | 相対スロット番号（0〜7のみ）| 指定不可 | 8 |

pt3ドライバーとpt1_drvは、`slot`を、直前に読んだTMCC情報（8個の配列）の添字としてしか使わず、範囲も検査しません。
TSIDを渡すと配列の外を読んでしまいます。
そこで`coaxd`は、`STREAM_ID`が8以上なら、ドライバーに渡す前にエラーを返します。
これらのノードで使う定義ファイルには、0〜7の相対ストリーム番号を書いてください（`coax export --channel-name transponder`がこの形で書き出します）。

この違いは、バックエンド名ではなく`GET /tune`の`relative_streams`で判別します。
値はTMCCのテーブルの大きさ（この2つなら8）で、識別子を受け付けるチューナーでは省きます。
NITはストリームを識別子で並べているので、`coax scan --discover`はこの値を見て、識別子を相対番号に直す必要があるか、いくつの番号を調べるかを決めます。

## LNB給電

3つのドライバーとも同じ規則です。

- `VOLTAGE`の指定が無ければ給電しません（pt3ドライバーには`LNB_DISABLE`を明示的に送ります）。`low`は11V、`high`は15Vです。
- チューナーを閉じるときにも給電を切ります。pt1_drvは`close()`でLNBの給電を切らないので、`coaxd`が切ります。
- 既定を「給電しない」にしている理由は[channel-files.md](../reference/channel-files.md#voltage)にあります。給電が必要な同軸に給電しなくても録画できないだけですが、すでに電源挿入器やブースターが給電している同軸にさらに給電すると、機材が壊れるためです。CATVのパススルーや共聴の同軸につながっていることが多いボードなので、指定が無い限り給電しません。

pt3ドライバーとpt1_drvのLNB制御には、次の制約があります。

- `LNB_ENABLE`に0を渡すと、「OFF」ではなく「モジュールパラメーター`lnb`の値を使う」という意味になります。そのため給電を切るときは必ず`LNB_DISABLE`を使います。
- **pt3ドライバーを`lnb_force=1`で読み込んでいる場合、この節の指定はすべて無効です**：給電はモジュールパラメーターの`lnb`で決めた電圧で常に入ります（[モジュールパラメーター](#モジュールパラメーターlnb給電をどこで決めるか)）。
- **LNBの給電はボードに1つで、ISDB-Sのチューナーを2本とも開いていると、2本目の指定はエラーにならずに無視されます**：先に開いたほうの指定がボード全体に効きます。
- 同じ理由で、2本使っているときに片方を閉じても給電は切れません。ドライバーが使用中のISDB-Sチューナーの数を数えていて、最後の1本になるまで`LNB_DISABLE`で何もしないためです（`pt3_pci.c`の`count_used_bs_tuners`）。

複数のボードを挿しても、互いに影響しません。
給電も、上のチューナーの数え方も、ボードごとに分かれているためです。
2枚目のボードのノードは`pt3video4`〜`7`と続き、並びも衛星2本、地上2本の繰り返しです。

## ロックと選局の戻り値

どのドライバーも、`PTX_SET_CHANNEL`（`SET_CHANNEL`）の中でロックを待ち、ロックしなければエラーを返します。
これは「選局はできたが信号が無かった」ということなので、`/tune`はエラーではなく`"locked": false`を返します。
ロック状態をあとから問い合わせるioctlはどのドライバーにも無いので、報告するロック状態は選局のときにドライバーが返したものです。`/tuners/{id}`も同じ値を返します。

| | 待ち方 | ロック失敗の戻り値 |
| --- | --- | --- |
| px4_drv | 10msごとに最大300回（約3秒）| `EAGAIN` |
| pt3ドライバー | 最大約2秒。ロックしたあともバッファを満たすため100〜200ms待つ | 独自のステータスコード（下記）|
| pt1_drv | 時間ではなく、I2Cレジスタを読む回数で決まる | 通常のerrno。衛星は`EIO`、地上波は`EINVAL` |

pt3ドライバーだけは、`SET_CHANNEL`の戻り値がerrnoではなく独自のステータスコードです（`pt3_com.h`の`STATUS`列挙体を負にしたもの）。
256や779といった値が来るので、errnoとして読んでも意味がありません。
`coaxd`は値を見て、次の4つを`"locked": false`として扱い、それ以外はコード名を付けたエラーにします。

| コード | 意味 |
| --- | --- |
| `PLLLockTimeout` | チューナーのシンセサイザーがロックしなかった |
| `PLLOutOfRange` | 同上 |
| `GeneralError` | 地上波の復調器が有効なチャンネルを報告しなかった |
| `InvalidParam` | 衛星の復調器が要求したストリームを返さなかった（名前はドライバーのもの）|

注意点が2つあります。

- **pt1_drvの衛星のロック報告は条件が緩くなっています**：ドライバーはTSIDのロック待ち（`ts_lock`）に失敗しても、それを無視して成功を返します。そのため、トランスポンダには同期したものの目的のストリームが取れていないときでも、`"locked": true`になることがあります。
- **pt3ドライバーのioctlは、ドライバー全体で1つのmutexを使って順番に処理されます**：`SET_CHANNEL`がそれを2〜3秒持つので、あるチューナーの選局中は、同じPCのほかのPT3チューナーへの操作（C/Nの読み取りも）が待たされます。これはドライバーの実装によるもので、`coaxd`の側では待たせていません。pt1_drvとpx4_drvはチャンネルやデバイスごとのロックなので、この問題はありません。

## 読み出し

TSは`read()`で読みます。
どのドライバーにも`poll`が無く、`O_NONBLOCK`も見ないので、読み出しは専用のループで行います。
細かい動作はドライバーごとに違います。

| | `read()`の挙動 | リングバッファ | あふれたとき |
| --- | --- | --- | --- |
| px4_drv | 渡したバッファが埋まるまで戻らず、途中でやめる手段が無い。ストリームを閉じるときは先に`PTX_STOP_STREAMING`を送る（リングを止めて、待っている`read()`を起こすのが、カーネルから戻らせる唯一の方法）| - | - |
| pt3ドライバー | データが無いと約600ms待ってから0バイトを返す（EOFではない）| 1チャンネルあたり約3.2MB | 古いデータが上書きされ、欠落は通知されない |
| pt1_drv | 64KiBたまるまで最大500ms待ち、たまらなければ0バイトを返す（EOFではない）| ISDB-T 2MiB、ISDB-S 4MiB | データを捨てるのではなく、DMAのスレッドが止まる。そのスレッドはボードの4チャンネルで共有しているので、1本の読み遅れがほかの3本も止める。読み出しを止めないこと |

## 信号測定

C/Nは`PTX_GET_CNR`／`GET_SIGNAL_STRENGTH`で読めますが、返るのは復調器の生カウンタで、dBではありません。
3つのドライバーともTC90522のスケールで返すので（CXD2856ERを載せたPX-MLT系は、px4_drvの中でTC90522相当の値に直してから返します）、`internal/coaxd/demod/tc90522`の変換曲線1組でどのデバイスも扱えます。

- pt3ドライバーが読むレジスタは、ISDB-Sが0xBC、ISDB-Tが0x8Bです。
- pt1_drvのISDB-Sはレジスタ0xBC/0xBDの16ビットで、pt3ドライバーと同じスケールです。ISDB-Tには注意が必要です。このドライバーが読むのはレジスタ0x8C/0x8Dの16ビットで、24ビットあるカウンタの下位16ビットだけです。カウンタが65535を超える範囲、おおよそC/Nが20.3dBより低いところでは値が一周してしまい、実際より良い値が出ます。ロックの判断には影響しません。

信号強度は、どのドライバーでも読めません。
ptx ioctlにそのためのものが無く、どのドライバーも用意していないためです（pt3ドライバーは中でAGCの値を読んでいますが、ioctlでは出していません）。

## カーネル組み込みDVBドライバーという選択肢（PT1 / PT2 / PT3）

PT1、PT2、PT3には、Linuxカーネル本体に入っているDVBドライバー（`drivers/media/pci/`の`earth-pt1`、`earth-pt3`）もあります。
こちらは`/dev/dvb`に出るので、`coaxd`の[`dvb`バックエンド](dvb.md)でそのまま使えます。

| | pt3ドライバー／pt1_drv（`chardev`）| mainlineの`earth-pt3`／`earth-pt1`（`dvb`）|
| --- | --- | --- |
| ドライバー | 別途ビルド | カーネル同梱 |
| 選局の指定 | `FREQUENCY`（`coaxd`がチャンネル番号に直す）| DVBv5のプロパティ |
| ISDB-Sのストリームの指定 | `STREAM_ID`は相対番号0〜7だけ | `STREAM_ID`にTSIDを書く |
| C/N | ○ | ドライバーが`FE_SCALE_DECIBEL`で値を返すかによる |
| 信号強度 | − | 同上 |
| 地上波の受信できる範囲 | VHF 1〜UHF 61／62 | UHF 470〜770MHzだけ（[下記](#ドライバーが申告する受信範囲)）|

2つのドライバーで同じボードを同時に使うことはできません。
どちらか一方だけを読み込んでください。

### ドライバーが申告する受信範囲

`dvb`バックエンドでPT3を使うと、VHF 1〜12とCATV C13〜C63を選局できません。
PT3の能力ではなく、カーネルの`tc90522`が申告する範囲（470〜770MHz）による制限です。
詳細と、カーネルに当てるパッチは[dvb.md](dvb.md#earth-pt3が受け付ける周波数の範囲)にあります。

VHFやCATVのパススルーを受信したいが、カーネルにパッチを当てたくない場合は、`chardev`でpt3ドライバー（[m-tsudo/pt3](https://github.com/m-tsudo/pt3)）を使ってください。
こちらはチャンネル番号のテーブルを持っているので、そのままVHFもCATVも受けられます。

## px4_drvと直接USBのどちらを使うか

px4_drvが対応しているデバイスは、`coaxd`から2つの経路で使えます。

| | `chardev` | `px4`ほか（[直接USB](px4.md)）|
| --- | --- | --- |
| px4_drv | 必要 | 読み込んでいると使えない |
| ファームウェア | ドライバーが持つ | `it930x-firmware.bin`が必要 |
| 対応OS | Linuxのみ | Linux / Windows / macOS |
| 伝送方式 | ISDB-TとISDB-Sだけ | デバイスが対応するものすべて（PX-MLT系のDVB-T/T2やJ.83も）|
| 信号強度 | 読めない | 衛星だけ読める |
| 内蔵カードリーダー | 使えない | 使える |

px4_drvが使用中のデバイスは、直接USBバックエンドでは開けません。
カーネルのドライバーがUSBインタフェースを確保しているので、usbfsの`claim`が`EBUSY`で失敗するためです。
そのため、px4_drvが使用中のUSBデバイスは、直接USBバックエンドの一覧には出ません。
px4_drvから外す手順は[os.md](../setup/os.md#カーネルドライバーからのunbind)にあります。

## 制限事項

- 受信できるのはISDB-TとISDB-Sだけです。ptx ioctlにはほかの伝送方式を指定する方法がありません。PX-MLT系のDVB-T/T2やJ.83は、直接USBバックエンドかLinux DVBドライバーで使います。
- 内蔵カードリーダーは使えません。px4_drvはIT930xのUARTを外に出しません（PT1/PT2/PT3にはスロット自体がありません）。
- 信号強度は読めません。
- Linux専用です。WindowsのPT1/PT2/PT3は[earthsoft-windows.md](earthsoft-windows.md)にあります。
